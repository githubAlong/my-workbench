# 我的工作台

教师个人工作台。首页看时间、天气、倒计时与今日事项；工作里管课时、课表、考勤、监考、出差、课件与笔记；日常随手记便签、布置作业；学习留积累；回收站找回误删。手机、iPad、电脑打开是同一份数据。

## 一、怎么跑起来

```bash
cd myworkbench
node server/index.mjs        # 或 ./run.sh
```

打开 <http://localhost:3000>。默认端口 3000，可用 `.env` 里的 `PORT` 改。

**环境要求**：Node.js ≥ 22.5（用了内置 `node:sqlite`），无需 `npm install`，零第三方依赖。

## 九、几个设计上的取舍

- **零依赖**：全站没用任何 npm 包，后端是原生 `http` + `node:sqlite`，前端是原生 ES Module。好处是部署不会因为依赖装不上而卡住，坏处是有些轮子得自己造（比如 multipart 解析、二维码绘制）。
- **软删除**：所有删除都是打 `deleted_at` 标记再进回收站，所以误删永远找得回来。
- **全局序号**：每条记录带一个跨表递增的业务序号，删了之后序号也不复用，方便和纸质台账对账。
- **数据只属于你自己**：所有查询都带 `user_id` 过滤，不同账号之间数据完全隔离。
- **主题靠 CSS 变量，不靠两份样式**：全站颜色都走 `:root` 的自定义属性，`html[data-theme="xxx"]` 只覆盖变量值。换主题时阴影、光晕、天气渐变、倒计时卡都用 `color-mix()` 从主色推导，所以加一套新主题只要补一段变量（约 35 行），页面代码一行都不用改。主题存在 `localStorage`（键 `wb_theme`），首屏内联脚本会先套用再渲染，不会闪一下白。

## 十一、教师考勤（坐班表 / 教研签到表）

「工作 → 考勤」下面按年级分两块，每个年级固定两个槽位：**教师坐班表** 和 **教师教研签到表**。没有表时是虚线的新建卡，点一下就建。年级默认内置「高一」「高二」，需要「高三」「初中部」时点年级条末尾的 `＋`。

### 两种表两套界面

| | 教师坐班表 | 教师教研签到表 |
| --- | --- | --- |
| 信息条 | 年级 · 日期 · 星期 · 节次 | 年级 · 日期 · 星期 |
| 行结构 | 姓名 + 学科 + 5 个勾选列 | 按学科分块，块头带签到进度条 |
| 勾选列 | 上课 / 坐班 / 听课 / 教研 / 请假 | 签到 |
| 底部汇总 | 各列人数 + 「N 人一项都没勾」 | 已签到 / 签到率 / 未签到人数 |
| 表格形态 | 一张长表，按学科排序 | 9 个可折叠的学科块，块头「全部签到」一键签 |

### 三种勾选状态（重要）

方块点一下循环 **空 → ✓ → × → 空**：

- **✓ 打勾**：做了
- **× 明确划掉**（虚线框）：确定没做，比如那天请假不上课
- **空白**：还没填

纸表上最常见的其实是「空白」和「划掉」两种，如果把它们当成一回事，汇总人数就会虚高。所以这里刻意拆成三态，底部「N 人一项都没勾」只统计真正空白的。

### 直接上传，自动识别

点「上传识别」，把 Excel（`.xlsx` / `.csv`）拖进去，服务端会自动解析：

1. **找标题行** —— 从标题里读出年级、表类型、年份，`2026年高一老师坐班表` 这种直接就对上了
2. **读日期行** —— `2026年10月19日 星期一 第 1-2 节` 拆成年 / 月 / 日 / 星期 / 节次
3. **找表头** —— 定位「姓名」所在行，右边连续的非空列就是勾选列
4. **识别双栏** —— 一页纸上左右并排印了两段（A4 省纸常见做法），表头里出现两个「姓名」时自动按姓名 + 学科去重合并成一张表
5. **值归一化** —— `√` `✓` `是` `到` `已签到` → 打勾；`×` `-` `/` `缺勤` → 划掉；空着就是空白

解析完先给你一张 **确认页**：年级 / 表类型 / 日期 / 节次 / 名称都可以改，下面列出「46 位教师 · 14 个学科 · 5 个勾选列」和**名册比对**（表里 46/46 人与名册一致），再往下一屏是前 60 行预览，确认无误才入库。

`.xls`（老格式）会提示「请在 Excel/WPS 里另存为 .xlsx」—— 老格式是二进制，为了零依赖不去啃它。

### 教师名册

「教师名册」按年级维护，导入表格时表里的人会自动补进对应年级的名册。所以：

- 新建空表时，会直接把名册里的人带出来（提示「将从名册带出 46 位教师」）
- 上传识别时会和名册比对，缺谁多谁一眼看见
- 名册支持「批量粘贴」，一行一个「姓名 学科」就行，从旧表格里复制过来即可

### 其它

- 表头「改日期/节次」可以随时改，改完不影响已有数据
- 搜索框按姓名 / 学科实时过滤，筛出来的行序号会重新从 1 排
- 「统计」按学科汇总某一列的完成率和未完成名单，适合拿去开年级会
- 「截图」把当前表格导出成 PNG，直接发群里
- 表格在手机上可以左右滑动，姓名列不会挤变形

### 纸质原件（照片 / 扫描件）

纸表填完，通常还要留个底。每张考勤表都能挂上它对应的**纸质原件**：

- 打开任意一张表，表头右侧点「原图 N」，可以看、可以加、可以删
- 上传 Excel 识别时，确认页里有「纸质原件（可选）」，顺手把照片选上，导入完成后自动挂到新表上
- 表格还在纸上、连 Excel 都没有？点「上传识别 → 表格还在纸上」，选年级 + 类型 + 日期 + 拍几张照片，会按名册先把名单铺好，你对着照片逐行打勾即可

照片存在 `uploads/<用户id>/` 下，一张上限 12MB，支持 JPG / PNG / HEIC（手机直出）。点缩略图会新开窗口看原尺寸。

> 提醒：这不是「拍照自动识别成表格」。目前只是把原件存下来方便核对；真正从照片里读出勾选，是下一步的事。

### 手机快速打勾（推荐日常用法）

46 个人一张表，在手机上一格一格点太费劲。表头右侧的「**快速打勾**」是专门为手机做的：

- 一屏只放**一位老师**，姓名大到能一眼看清
- 下面是该表所有勾选列的大图块（坐班表 5 个、教研表 1 个），点一下循环 **空 → ✓ → × → 空**
- 图块按列数自动收窄并居中：5 列排满一行，只剩 1 列时居中显示，不会被拉到角落
- 这一行的勾选列**填满就自动跳到下一位**，不用点「下一个」
- 顶部进度条 + `12 / 46`，底下提示「还有 N 人没填」
- 只过**完全空白**的人；如果全场都填过了，就变成逐个复核模式
- 「跳过」留着不填直接过，「上一位」可以回头改
- 「保存并关闭」一次性提交，中途退出不会丢已点的内容（关掉再进会重新开始）

实测在 390px 宽的手机上，5 个图块排成一行、不换行、不横向溢出，单手拇指够得到。

### 导出横版 A4 PDF，直接打印

表头「**PDF**」按钮，一次性拿到横向 A4 的纸质版：

- 服务端用 WeasyPrint 渲染，中文字体嵌进 PDF，任何设备打开都不缺字
- 46 人的坐班表正好 **2 页**，第 2 页表头自动重复
- 行不跨页断开，底部汇总条跟着表格走
- 文件名为表格名，手机上点下载后可以直接转发到微信/企微群
- 导出前会先把当前编辑内容存一遍，所见即所印

> 依赖：`python3` + `weasyprint`。没装的话 PDF 按钮会提示，其它功能不受影响。

### 为什么没有做「拍照自动识别勾选」

这个想法试过，结论是**不做**，理由不是技术做不到，而是做出来会害人。

用 Tesseract 5.3.4 加中文包，在一张印刷清晰、正对着拍的纸表上跑：

| 项目 | 结果 |
| --- | --- |
| 10 个姓名 | 错了 6 个（`李成华`→`地成华`、`徐洁`→`徐尘`、`覃蓉`→`现实`） |
| `✓` 勾选 | 被认成 `V`、`<`，还和 `×` 混在一起 |
| 列位置 | **整体错位** |

最要命的是**列错位**：勾选本来就只是一个符号，一旦列对不上，每个老师的状态都会张冠李戴，而表面上看不出任何异常。用手机随手拍（缩小 + 轻微倾斜）结果更差，会认出「党水」「涝衬」这种根本不存在的人。

而且名册已经有了 —— 姓名不需要从照片里读，本来就知道。OCR 唯一能省的是「点 46 下」，但如果为此引入一个**看不见的错误来源**，后续核对 230 个格子的成本远高于 46 次点击。

所以最终做法是：照片存档给人核对，「打勾」这件事用极致优化的手动操作解决。

## 十二、学习（计时 / 统计 / 笔记）

入口：**学习**。三个 Tab：记录 / 统计 / 笔记。

### 计时器：状态在服务端，不在浏览器

上课或自学想记时长，最烦的是「中途切出去回个消息，回来时间没了」。所以计时状态**存数据库**（`studies` 里 `source='running'` 的那条草稿），前端只负责显示：

| 你的动作 | 结果 |
| --- | --- |
| 点「开始」 | 建一条 `source='running'` 草稿，记下 `started_at` |
| 切到微信、锁屏 | 不影响。回来重新算 `now - started_at - paused_ms` |
| 刷新页面 / 换设备登录 | 照样接着走，因为时间是从库里算的 |
| 点「暂停」 | 记 `paused_at`，`paused_ms` 不变 |
| 再点「继续」 | `paused_ms += now - paused_at`，清空 `paused_at` |
| 点「结束并保存」 | 转成 `source='timer'` 正式记录，时长四舍五入到分钟 |

```js
// server/index.mjs
const elapsed = Math.max(0, now - start - pausedMs);
// paused_at 有值时 now 用 paused_at，所以暂停期间 elapsed 是冻住的
```

前端那个每秒跳的 `#tm-clock` 只是**显示用的秒表**，它的值不参与任何计算。切后台时用 `visibilitychange` 停掉本地 tick（省电），切回来自动重启；离开页面时 `onViewLeave` 一并清掉定时器。**哪怕本地秒表跑歪了，刷新一下就恢复真值。**

启动时会收尾孤儿草稿（上次进程被杀、没走「结束并保存」）：按 `started_at` 到现在补算时长存成正式记录，并打一行日志。

### 统计：月视图看分布，年视图看趋势

- **月视图**：热力日历（每天一格，颜色深浅按时长分 4 档）+ 分类占比条 + 四宫格（本月合计 / 记录条数 / 学习天数 / 日均）
- **年视图**：12 个月柱状图 + 年累计 / 记录条数 / 月均 / 最高月 + 全年分类排行

两个视图都排除 `source='running'` 的草稿，未结束的计时不会被算进统计。

### 月度目标可改，且没写死

默认 10 小时，但**存在 `users.settings.study.goalHours`**，点目标卡片上的铅笔随时改。翻到历史月份时，标题从「本月目标」变成「N 月目标」，避免文案对不上。

> 别把目标写死在代码里：同一个人上个月兴致高定 20 小时、这个月忙只定 5 小时，写死就废了。

### 笔记复用同一个库

「学习 → 笔记」和「工作 → 笔记」读写的是**同一张 `notes` 表**，共享分类和搜索。理由很简单：知识库不该因为入口不同而分裂成两份，"我看过的书"和"我备的课"本来就是一件事。

### 三处踩过的样式坑

1. **热力格溢出卡片**：`grid-template-columns: repeat(7, 1fr)` 里的 `1fr` 最小宽度是**内容宽度**，7 列加起来撑破容器，30/31 号被截掉。改成 `repeat(7, minmax(0, 1fr))` + 固定 `height`（不用 `aspect-ratio`）。
2. **原生 `<input type="month">` 显示英文**：中文环境下它会渲染成 "October 2026"。改成隐藏原生输入，只当取值器用（`.month-hidden` + `showPicker()`），界面上自绘「◀ 2026 年 10 月 ▶」。
3. **暗色主题下格子消失**：热力格底色调的是 `--bg-sunken`，在深色主题里是 `#0a0a0c`，跟卡片 `#1c1c1e` 几乎同色，整片格子看不见了。改用 `--line`（暗色 `#38383a`）才有层次。**凡是"比卡片再深一层"的底色，都要在六个主题里各看一眼。**

## 十三、我的（资料 / 安全 / 消息中心）

入口：**我的**（手机端底部导航最右）。子页 `#/profile`（个人信息）、`#/messages`（消息中心）。

### 头像：前端裁切 + 服务端双重校验

只靠前端限制等于没限制——curl 一样能传 10MB 的文件上来。所以两边都卡：

| 关卡 | 做什么 |
| --- | --- |
| 前端 | 选图后 `cropSquare()` 用 canvas **居中裁成正方形**、缩到 512×512、压成 JPEG 0.9，超过 2MB 直接本地拦下 |
| 服务端 | 校验 `Content-Length`/实际字节 ≤ 2MB、MIME 必须在 `image/jpeg|image/png` 白名单里，否则 400 |

提示语带上实际值，用户知道该换多大的图：

```
图片不能超过 2MB（当前 2.3MB）
只支持 JPG / PNG 格式
```

换头像时把旧的文件记录标软删（`attachments.deleted_at`），不然反复换头像磁盘会一直涨。

### 改密码

旧密码校验 → 新密码 ≥ 6 位 → 两次一致。三个条件任一不满足就本地拦住，不发请求。服务端仍然要用 `crypto.scrypt` 重新加盐哈希，**不存明文、不留旧密码的任何痕迹**。

### 消息中心：四类筛选 + 点消息直接跳

| 类型 | 来源 |
| --- | --- |
| `task` | 今天还没做完的事项 / 便签（打开消息中心时同步生成） |
| `remind` | 事项设了提醒时间，到点了 |
| `system` | 系统通知 |
| `work` | 工作相关 |

每条消息带 `link`（跳转地址），点一下先标已读再 `go()` 跳过去，不用自己找。

**去重靠 `dedupe_key`**，形如 `item-{id}-{date}`、`todo-{id}-{date}`，同一个对象一天只提醒一次。因为同步逻辑挂在「打开消息中心」这个动作上，不挂定时器——够用，且服务器不用一直醒着。

> **踩过的坑**：同一件事会同时产生两条消息 —— 设了提醒时间的出 `remind`，任务同步又出一 `task`，标题一模一样。现在 `pushMessage` 支持 `skipIfSameTitleToday`，按「标题 + 当天」再去一道重，先到的那条（通常是 `remind`，信息更全）留下。

### 桌面端要收窄

手机上「我的」是紧凑单列，铺到 1100px 后每行左图标右箭头、中间一大片空白。加了个页面级类名收窄到 720px 并居中：

```css
@media (min-width: 900px) {
  .page-me { max-width: 720px; margin: 0 auto; }
}
```

`main.classList.add('page-me')` 放在视图入口，因为 `render()` 每次都会重建 `main` 节点，加类不会漏到别的页面。

## 十四、一个框架级的坑：`null` 是合法的响应体

`server/index.mjs` 的请求分发原来是这么写的：

```js
const out = await match.handler(req, res);
if (out && !res.headersSent) json(res, out);   // ❌
```

`out` 为 `null` 时这个条件为假，**响应永远不发出，请求就那么挂着**，前端表现为转圈直到超时（curl 里是 `HTTP 000`）。

`GET /api/study/timer` 在「当前没有在计时」时正好返回 `null`，于是整个接口完全不可用。查了半天以为是路由冲突、多进程抢端口，最后加日志才看到 handler 全部执行完、返回值也拿到了，就是没发出去。

```js
if (!res.headersSent) json(res, out === undefined ? null : out);   // ✅
```

> 教训：**判断"有没有返回值"不能用真值判断**。`null`、`0`、`""`、`false` 都是合法响应体。要区分的是 `undefined`（没写返回值）和「写了但是空」。

## 十五、上课（课时统计 & 代课对账）

入口：**工作 → 上课**。这个模块解决一件事：**月底算清「谁该给谁多少钱 / 多少节课」**，并且能在财务那里讲明白。

### 一条记录就是一次授课事实

每条记录记的是「**某天某一节，某个班到底谁上的**」，而不是「我上了几节」。这个视角决定了后面所有设计。

| 字段 | 说明 |
| --- | --- |
| 上课时间 / 节次 / 班级 | 三门基础信息，可从周课表一键带出 |
| 上课内容 / 教学进度 / 下一节课内容 | 备课三件套。列表里「下一节内容」压成内容下方的灰色小字，回看最顺手 |
| 违纪情况 / 备注 | 备查 |
| 代课类型 | 正常上课 / 我代别人上 / 别人代我上 / 换课 |
| 对象（peer_name） | 代课时对方是谁，名册可选也可手填 |
| 课时（hours） | **这节课实际算几节课**。别人代我上时固定为 0 |
| 课时口径 / 金额 | 结算用的数值，默认自动填，可手工改 |

### 四种代课怎么记账

核心规则一句话：**一节课的课时只归一个人。**

| 场景 | 记录长什么样 | 课时归谁 | 月底怎么算 |
| --- | --- | --- | --- |
| 正常上课 | 我 → 高二(3)班 第1节 | 我 | 计入我的课时 |
| 别人代我上 | 我 → 高二(3)班 第1节，对象=王老师，课时=**0** | 王老师 | 我 **应付** 王老师 1 节 |
| 我代别人上 | 李老师 → 高二(5)班 第3节，代课人=我，课时=1 | 我（额外） | 我 **应收** 李老师 1 节 |
| 换课 | 我和张老师互换，只留说明 | 各归各的，课时不变 | **不计账**，仅备查 |

因为「别人代我上」这条记录的 `hours` 存的就是 **0**，所以底部那个统计就是一句朴素的 `SUM(hours)`，**没有任何 if 判断**。少写条件 = 少一个出错的地方。

### 三个数字并排显示（去财务对账的关键）

页面上永远是这三个数：

```
课表排课 74 节  =  实际授课 3 节  +  请假代课 2 节
```

- **课表排课**：按周课表整月推算出来的「本该上多少」
- **实际授课**：真正算我课时的节数（正常 + 我代他人 + 换课）
- **请假代课**：我请假、别人替我上的节数（课时归对方，不含在我这里）

这三个数的意义是：**74 − 3 = 71 的差额，一行字就能解释清楚**。财务问「你怎么少了这么多课」，不需要翻记录，指着这一行即可。当月还没过完时会额外提示「本月才过 24/31 天，排课数按全月推算」，避免自己吓自己。

### 课时口径与金额是两列独立的值

有些学校按节数结，有些按钱结，还有的按「打折的课时」结。所以两个值分开存：

- `pay_hours`（课时口径）：默认等于课时，可改（比如一节课算 1.5 课时）
- `pay_amount`（金额）：默认 = 课时口径 × 单价，可改（比如这次补课按 40 元算）

两列都是**录入时的快照**，之后改单价**不会追溯已录的记录**。这是故意的 —— 已经跟人对过账的钱不能悄悄变。

单价在页面顶部「单价 60 元/节」里改，只影响之后新录的记录。

### 结清（两种粒度，都支持反悔）

「跟谁结算」区域按人聚合，每人一行：应收/应付、几节、多少钱，右边两个按钮。

**全部结清** —— 这个人当月所有记录一次性结掉。

**逐节结** —— 点开后有勾选框，列出这人**还没结的每一节课**（日期 / 节次 / 班级 / 节数金额）。

这是按现实来的：今天先给王老师两节课的钱，剩下的一周后再结。

| 操作 | 结果 |
| --- | --- |
| 勾两条 → 结清选中的 | 这 2 条打上 `settled_at`，剩 1 条 |
| 行上显示 | `还剩 1 节 / 60 元（已结 2/3 节）` + 「部分结清」灰标 |
| 全部结完 | 变成「已结清」，按钮只剩「撤销结清」 |

净额只算**未结清的那部分**，所以：

- 3 节 180 元 → 结掉 2 节 → 净额自动从 −180 变成 −60
- 撤销其中一条 → 净额又回到 −60

不会出现「已经给过钱又算一遍」，也不会因为「只结了一部分」就整月卡住。

数据上每个人的记录分两组数字：`hours/amount` 是当月总计，`open_hours/open_amount` 是还没结的部分。净额用后者算。

### 一键带出周课表

新增记录时，如果今天有课，顶部直接列出今天的每一节（节次 + 班级 + 时间），点一下就把日期、节次、班级、科目、起止时间全填好。

今天没课（比如周末备课）会自动找**下一个有课的日子**，提示里写明「点一下会把日期改到周一」，点了连同日期一起挪过去。

### 竖版 A4 对账单

页面右上角「对账单」生成一份可打印签字的正式单据（竖版 A4）：

1. **课时汇总** —— 三口径并排 + 明细行 + 本期净额
2. **分人结算明细** —— 跟谁、什么方向、几节、多少钱、是否已结清
3. **逐节明细** —— 日期 / 节次 / 班级 / 内容 / 课时 / 代课说明，课时为 0 的灰显并加脚注
4. 底部「本人签字 / 日期」「财务核对 / 日期」两条签章线

十来条记录能排进一页；记录多了会自动分页且每页重复表头，签字块永远整块落在同一页，不会被切成两半。

> 依赖：`python3` + `weasyprint`，和考勤导出共用同一套环境。

## 十六、监考（三种情况，两本账）

监考的麻烦在于**同样是监考，钱的性质完全不同**。所以这里不按「一次监考」记一笔钱，而是先分清这一场属于哪种情况。

### 三种情况

| 类型 | 什么场景 | 谁给谁钱 |
| --- | --- | --- |
| 学校分配 | 学校统一排的监考 | 学校打到工资卡 |
| 我代别人 | 同事找我替监考 | 同事私下给我 |
| 别人代我 | 我找人替我监考 | 我私下给同事 |

### 学校那笔钱不进私账

这是最容易算错的地方。学校监考费是**统一发到工资卡**的，根本不经过同事间的私下转账。如果把它混进「净额」，就会出现「李老师欠我 50、学校欠我 60，所以净应收 110」这种自欺欺人的数字——实际上学校那 60 你连要都不用要，到点自己打卡里。

所以顶部第一张卡单独显示：

> **学校应发 XX 元** —— 这个月还没到账的学校监考费，点一下卡片上的「标记已到账」就清零。

**同事间净额 = 我该收 − 我该付**，只算私下转账的那部分，和学校那笔完全隔开。

### 计价规则（一场一价 or 按分钟分档）

右上角「计价」打开规则设置，两类分开配：

- **同事之间**：固定一场一口价（默认 50 元/场），替谁监考都是这个数。
- **学校分配**：两种算法，默认「按场次」每场固定（默认 60 元/场）；如果你们学校按时长发，切成「按时长」后按分钟分档（默认 90 分钟以内 50 元、150 分钟以内 70 元、更长 90 元）。

录入时会**自动算好金额再让你确认**：填完起止时间，时长自己算出来，金额跟着规则填进去。想手改也行，改完以你填的为准。规则的默认值是我按常见情况猜的，你按自己学校的实际标准改一次就长期生效。

### 录入：一个三选一

打开「记一场监考」，第一行就是三选一：

```
[ 学校分配 ]  [ 我代别人 ]  [ 别人代我 ]
```

选完下面自动变：选「学校分配」隐藏「对方老师」（学校监考没有对手方），换成「学校这笔到账了吗」；选另两种时才出现「对方老师」输入框，而且会**记住你之前录过的同事名字**，下次直接选。

### 结清：按场勾选

跟上课模块一样支持两种粒度：

- **全部结清** —— 这个人的本月全结掉。
- **逐场结** —— 点开列出每一场（日期 / 考试 / 考场 / 金额），勾哪场结哪场。现实里你确实可能今天先结两场、剩下的改天再说。

结清后行上显示「已结清」或「还剩 X 元（已结 M/N 场）」，随时可撤销。已经结清的部分自动从净额里扣掉。

### 手机上看

监考明细在手机上也是卡片式：日期 + 金额在头，类型标签单独一行，考试名和考场在中间，时间和结算状态在底部。表格不横向滚动。

### 和其它模块的关系

监考的日期、起止时间同时写进了旧字段（`date` / `start_at` / `end_at`），所以首页日历和今日日程里能正常显示监考安排。

> 暂未和上课模块联动（比如「上午监考导致下午的课要调」目前要两边各记一次），先跑通独立流程。

## 十七、班级短链（课件 + 签到 + 抽题）

一个链接发给学生，不用装 App、不用注册。地址形如 `https://你的域名/s/2b66ah`，在「工作 - 课件」页顶部复制。

### 为什么是短链，而不是让学生登录

学生手边只有手机，一节课四十几个人，任何一步多余的注册都是在消耗课堂时间。所以这里只做一件事：**点开就能用**。

学生第一次填一次姓名或学号，之后浏览器记住，下次打开直接是「你是 张一诺」+　三个按钮。

### 签到：把「当场」和「留痕」压成一步

这是这个模块真正的价值。以前点名是纸名单打勾，课后还要再录一遍；现在：

1. 你在「工作 - 课件」点「开始签到」，选班级和节次。
2. 学生打开短链，页面**默认就停在签到页**（有进行中的签到时会亮红点）。
3. 学生点「我到了 / 迟到了 / 请假」，你那边的人数实时长出来。
4. 下课点「结束」，学生端签到入口消失，记录留着。

你的界面上每条签到显示 `已到 38/40 · 迟到 1 · 请假 1`，点「看明细」还能看到：

- **四格统计**：到了 / 迟到 / 请假 / 未到
- **已签名单**：谁点的、什么状态、是不是你代标的
- **未到名单**：直接列出还没出现的名字，点名字可以当场补标「已到 / 请假」

### 实时是怎么做的（自动轮询）

有进行中的签到时，页面每 **3 秒**拉一次数据，卡片标题旁会亮一个呼吸的「实时」角标。人数一变，数字会轻轻跳一下并变绿，一眼就能看出「刚才又有人签了」。明细弹层也一样实时。

拉的时候**只改数字，不重绘整张卡**：所以你点按钮、滚动页面都不会被打断，也不会闪。

什么时候停：

| 情况 | 行为 |
| --- | --- |
| 没有进行中的签到 | 一次都不拉（平时零开销） |
| 签到全部结束 | 自动停，并整体刷一次让「结束」按钮消失 |
| 切到别的模块 | 自动停（视图卸载钩子 `onViewLeave`） |
| 浏览器切到别的标签页 | 暂停；切回来立刻拉一次 |
| 关掉明细弹层 | 停 |
| 上一次请求还没回来 | 跳过本轮，不叠加请求 |

> 实现见 `public/js/core.js` 的 `startPoll()`——用 `setTimeout` 递归而不是 `setInterval`，慢网络下不会堆积请求；任何视图要用轮询都复用它，记得把返回的 `stop` 交给 `onViewLeave`。

### 会防止的几种脏数据

| 情况 | 处理 |
| --- | --- |
| 学生没填名字就点 | 前端拦住，提示先填学号或姓名 |
| 名字打错（如「张三丰」） | 后端核对名册，提示「名单里没有这个人」 |
| 同一个人点两次 | 按归一化姓名/学号去重，第二次覆盖第一次，不会变成两个人 |
| 全角/半角、空格差异 | 统一转半角去空格再比对 |
| 点错了身份 | 结果页有「不是我，换个名字」，也可以直接再点一次改正 |
| 同一班同一节重复开始 | 接上原来那场，不会开两场 |

### 抽人

选班级 → 点一下 → 弹出名字。就这三步，没有别的参数要填。

- **优先用名册里的真名**。你维护过名单的班级，抽出来就是「朱怡然」这样的名字，不是学号。
- **没有名册也能用**：按班级人数生成 1~N 号来抽（显示成「15 号」）。
- **同时抽几个人**：右边填数字，1~10 个，多人时并排展示。
- **不重复抽同一人**：打开开关后，本轮抽过的人不再出现，页面底部显示「已抽 4/40，还剩 36」。全班抽完会自动洗牌，下次重新开始。
- 滚动过程模拟真人翻名单（从全班名字里快速跳动），停下来才揭晓，末尾有轻震动。

### 惩罚盲盒

- 学生点「开箱」，盒子摇晃 → 揭晓谜面 → 按强度分三档：**轻松 / 有点挑战 / 大冒险**（对应 `light / average / heavy`）。
- 学生签过到的，页面上会显示「给 黄雨桐 抽的」，记录也带上名字；没签到就是匿名。
- 开箱即留痕，写入 `punish_records`，你在「工作 - 课件」的盲盒卡片里能看到今天学生抽到了什么、几点抽的。

你在教师端的盲盒卡片里可以：

| 操作 | 说明 |
| --- | --- |
| 加任务 | 写内容 + 选强度，立刻进盲盒 |
| 编辑 / 删除 | 每条右侧两个图标 |
| 补经典任务 | 一次补 12 个经典项（唱歌、深蹲、领读、英文自我介绍…），**自动跳过已存在的**，重复点也不会加重复 |

> 强度只是给学生看的标签，不影响抽中概率——每个任务等概率。想少抽到「大冒险」，就把那几条删掉或降级。

### 隐私取舍

学生**只能看到自己的状态和本班已签人数**，看不到其他同学的名字。未到名单只有你能看到。这是刻意的——把全班名单暴露给任何拿到链接的人，风险不值得。

> 链接本身是访问凭据，别发到公开群里。需要停用就在「课件」页把短链的开关关掉（或在 `student_links` 里把 `enabled` 置 0）。

### 一个链接只服务一个账号

短链是**绑账号**的：`student_links.user_id` 指向谁，学生打开就只能看到谁的班级、课件、任务、签到。

所以别的老师**不能直接用你的链接**——不是技术上打不开，而是他打开只会看到你的内容，他自己的班和课件他改不了，等于白搭。他需要自己注册一个账号，系统会自动给他生成一条属于他的短链。

好处是隔离彻底：学生 A 班的人拿到你班链接，也不会串到别的老师的数据里去。

### 两个踩过的坑（改代码时注意）

**1. 班级名不能直接拼**

数据库里 `class_name` 存的是 `高二(5)班`，`grade` 也是 `高二`，直接 `${grade} ${class_name}` 会渲染成「高二 高二(5)班」。统一用 `clsName(grade, cls)`：班级名已含年级就只用班级名，否则才补前缀。这个函数在 `public/js/core.js`（教师端）和 `public/student.html` 内联脚本里各有一份。

**2. 学生链接必须带上访问凭据**

平台要求所有页面带 `?sharecode=...`，裸的 `/s/2b66ah` 会被拦成「链接不完整」。生成学生链接一律走 `studentUrl(code)`（`public/js/work.js`），它会把当前的 `sharecode / code / access` 参数透传过去。显示、复制、预览三处都用它，不要自己拼 `location.origin + '/s/' + code`。

## 十八、出差 / 报销

三本账分开算，互不污染：

| 账本 | 内容 | 要不要票 |
| --- | --- | --- |
| 实报实销 | 交通、住宿、打车、过路费、停车费、其他 | 要 |
| 定额补贴 | 伙食 + 市内交通，按天数定额 | 不要 |
| 预借 | 出差前领的钱，从应报里扣 | — |

**应到手 = 实报 + 补贴 − 预借**。这个算式直接印在每张出差卡上，不用点进去就知道能拿多少。

### 两种记账方式，不重复算

一笔支出可以记在**主表**（新建出差时的那些金额框），也可以记在**明细**（点进「明细 / 发票」一笔一笔加）。两边都填了不会翻倍——`calcTrip()` 按 `kind` 汇总明细，跟主表同类别取**较大者**：

```js
const byKind = {};
for (const it of items) {
  const k = ['transport','hotel','taxi','toll','parking'].includes(it.kind) ? it.kind : 'other';
  byKind[k] = n2((byKind[k] || 0) + n2(it.amount));
}
for (const k of Object.keys(byKind)) {
  if (byKind[k] > real[k]) real[k] = byKind[k];   // 取较大者，避免记两遍翻倍
}
```

> 为什么取较大者而不是相加：主表填「交通 186」通常就是明细里那笔高铁，两边都加会变成 372。取较大者在两种记法下都成立。

### 发票：不强制，但大额会催

- 每笔明细可以标「有票 / 没票」，没票的那行标橙色「无票」。
- **住宿 / 交通类 ≥ 100 元**算大额，没票会在卡片上标「缺票 N」，详情页还会出一条橙色提醒，建议补票再交。
- 伙食补贴本来就没票，不算进缺票统计——不会被无意义的提醒烦到。

### 一键复制报销单

出差卡和详情页都有「复制报销单」，点了直接进剪贴板，粘给财务就行：

```
【差旅报销单】王老师　2026-10-20 至 2026-10-22　共 3 天
事由：省级语文教研培训
行程：学校 → 省城教科院

一、实报实销
　交通费：¥186
　住宿费：¥320
　市内打车：¥48
　小计：¥674

二、定额补贴（无需发票）
　伙食补助：¥300（100/天 × 3 天）
　市内交通补助：¥120（40/天 × 3 天）
　小计：¥420

三、预借/垫付：¥500

合计应报：¥1094　扣除预借后应补：¥594
```

浏览器不支持剪贴板（老 Safari 或非 https）时会自动弹出一个全选好的文本框，长按复制即可，不会白点。

### 补贴标准

「补贴标准」按钮里改，默认 **伙食 100/天 + 市内交通 40/天**，各地标准不一样按自己单位填。改完所有历史记录的补贴会自动重算——因为标准是**算的时候读**，不是记账时存档。

### 统计

「统计」是当年视角：四宫格（次数 / 里程 / 应报合计 / 未到手）+ 12 个月柱状图 + 「钱花在哪」分类占比。柱状图只给有数的月份画柱子，空月份不画——避免 0 元也立一根小横杠被误读成有数据。

### 路由顺序坑

`/api/trip/stats` 必须注册在 `/api/trip/:id` **之前**，否则 `stats` 会被当成 id 匹配走，返回「出差记录不存在」。同理 `/api/trip/:id/text` 放在后面没问题（多一段路径不会撞），但新增类似 `/api/trip/xxx` 的静态子路径时，一律往 `:id` 上面放。

## 十九、首页（时钟 / 天气 / 倒计时 / 日历 / 便签）

首页是整个工作台的门面，信息密度最高，所以布局原则是**上轻下重、左右分栏**：

```
┌───────────────┬───────────────┐
│  时钟 + 问候   │   天气（简）    │   ← 顶栏等高两张卡
├───────────────┴───────────────┤
│  倒计时通栏（下一个事项 + 抢答） │   ← 通栏
├───────────────────────────────┤
│  搜索                          │
├───────────────────────┬───────┤
│ 今日事项 + 便签输入行   │ 日历   │
│ 今日课程               │ 当日日程│
│ 每日一句               │ 消息   │
└───────────────────────┴───────┘
```

### 每秒刷新的铁律：只改数字，绝不重画

时钟和倒计时都按秒跳。如果每秒 `innerHTML = ...` 重建一次，手机上会每秒重排 + 重绑事件，滑动直接卡住。

做法：
- 时钟只改 `.hm` / `.sec` / `#clock-date` / `#clk-foot` 的 `textContent`；
- 倒计时用 `cdKey`（事项 id + 目标时间）判断结构有没有变，变了才重建整块，否则只改 `[data-cd="d|h|m|s"]` 四个节点；
- 「第 N 周 · 本月还剩 N 天」这种一天只变一次的行，用 `lastFootKey` 做日期 key 挡一道，跨天才重算。

> **踩过的坑**：`refreshHome()` 会重建 `main.innerHTML`，但 `lastFootKey` / `lastGreetKey` / `cdKey` 还是旧值——新节点因为 key 没变就一直空着（症状是底部周数整行空白）。修法是在 `renderHome()` 里、`startClock()` 之前把这三个 key 清空。**凡是"上次渲染过什么"的记忆变量，DOM 一重建就必须归零。**

### 顶栏：时钟卡 + 天气卡

- 时钟卡：问候语 + 铃铛/主题按钮一行 → `22:15:33`（秒小一号、主题色）→ 日期 + 星期徽章 → 底部 `第 43 周 · 本月还剩 7 天`。
- 天气卡默认只显示**城市 / 定位 / 温度 / 天气 / 今日区间 / 穿搭一句**，点「详细天气」才展开湿度、风速、降雨、紫外线、日出日落、逐小时预报和 7 天预报。展开/收起状态记在 `localStorage`，下次进来不用再点。
- 两张卡用 `height: 100%` 强制等高，视觉上成为一条。

> **踩过的坑（展开态）**：展开后天气卡要跨两列，这里连踩三个：
> 1. `.topbar > .card { height: 100% }` 在跨列元素上会按"单列高度"算，撑成 2 倍高 —— 必须在展开态把它归零；
> 2. 只归零还不够，grid 默认 `align-items: normal`（= stretch）会把跨行元素按"两行总高"拉伸，得配 `align-items: start`；
> 3. 最后才发现真正的原因是内容重复录入：`weatherHTML()` 里既画了大温度块，又画了指标/穿搭/小时块，两套叠在一起自然超高。把「指标 + 穿搭 + 小时」拆成独立的 `wxMetricsHTML()`，展开区改成 `左列详情 / 右列 7 天预报` 两栏，问题一起消失。
>
> 教训：**布局算不对时，先怀疑内容重复渲染，再怀疑 CSS。**

### 倒计时：自动算下一个事项

按 `collectCdCands(now)` 收集候选（今天剩余的事项、课程、监考、出差），取最近的一个。**今天什么都剩不下时自动退回「明天上午第一个」**，标题上方那行从「下一个」变成「今天没有别的了 · 下一个」，不会出现一个空壳。

### 日历：月视图可折叠成周

- 苹果手机那种月视图：7 列网格、今天实心圆、选中日淡底、每格下方最多 4 个小圆点表示当天有什么（蓝＝事项、青＝上课、橙＝监考/出差、紫＝提醒）。
- 点「周」把 35/42 格**切片成当前选中的那一周 7 格**，格子加高（52px）看得更清；点「月」恢复整月。
- 折叠只重画网格，**不重拉数据**，年月和选中日都保持不变——切来切去不会跳走。
- 手机端（≤520px）日历头一行塞不下 5 个控件，所以「周/月」和「年月」按钮只留图标，图标本身已经能说明干嘛。

### 便签式快速添加

并进「今日事项」卡片底部一行：`✎ [想到什么先记一笔，回车保存…] ⏱ [保存]`。

- **回车即存**，存完刷新后焦点自动回到输入框，可以连着记第二笔；
- 可选的 ⏱ 给这条便签加个时间，存成带提醒的事项；
- 存的这条会同时出现在「今日事项」和「日常 → 便签」，`source` 标记为「来自便签」，列表里带一个橙色小标。

> 事项行原本右侧有个 `⋯` 按钮，实际渲染出来是一串乱码小点。现在改成**整行文字区域可点即编辑**（hover 有底色反馈），去掉多余图标，行更干净、点击热区更大。

### 时区：日期口径一律按 UTC+8

部署机跑在 UTC，而你在北京。这中间有个只在**凌晨 0 点到 8 点**出现的坑：

`created_at` 存的是 UTC 时间串，SQL 里 `substr(created_at,1,10)` 拿到的就是 UTC 日期。北京时间 10 月 25 日 00:56 时 UTC 还是 10 月 24 日 16:56 —— 于是服务器认为"今天"是 24 号，前端传的也是 25 号，两边对不上。症状是：**便签回车保存提示成功，但「今日事项」里就是没有。**

修法（`server/helpers.mjs`）：
- `cnDate()` —— 按 UTC+8 取今天，所有默认日期都改用它，不再用 `fmtDate(new Date())`；
- `isoToCnDate(iso)` —— 把 UTC 时间串换算成北京日期；
- `todayDigest()` 里时间戳归属不再靠 SQL 的 `substr`，改在 JS 里判定：**有 `start_at` 按它归属，没有的（便签）按创建时间的北京日期归属**。

> 教训：只要服务器时区 ≠ 用户时区，"按日期分桶"这种查询就一定会出错。日期到底算哪天，要由**服务器按用户时区**说了算，别指望前端传值把洞补上。

### 每日一句

中英对照，英文带小喇叭（`speechSynthesis`，优先挑 `en-US` 音色），底部「换一句」随机换。喇叭播放时有脉冲动画，播完自动停。

## 二十、日常（便签流）

【日常】是手机便签式的随手记，和首页的快速便签**同一份数据**，只是换了种看法。

### 三种状态

只有「未开始 / 进行中 / 已完成」，不做标签。卡片左侧一条竖色条 + 底部一枚 chip 表达状态：

| 状态 | 色条 | chip |
|---|---|---|
| 未开始 | `--primary` 蓝 | blue |
| 进行中 | `--amber` 琥珀 | amber |
| 已完成 | `--green` 绿 | green |

点 chip 是**三态循环**（未开始 → 进行中 → 已完成 → 未开始），右侧圆圈是**一键完成/取消**。两个入口一个改状态、一个只切完成，互补。

### 状态同源（最容易坏的地方）

首页的便签和日常的便签其实是两张表：

- `items`（source = '便签'）—— 首页「今日事项」里显示的那条
- `todos` —— 日常列表里的那条

靠 `todos.ref_item_id ↔ items.ref_id` 双向绑定，两边的 PATCH 路由各自同步过去。**`/api/quick` 写入时必须把两边的 id 互相回填**，否则绑定是空的，同步逻辑写了也白写——这个坑踩过一次，表现为「首页勾了完成、日常还是未开始」。

启动时有一段自愈（`relinkTodos`），把历史遗留的孤儿记录按标题关联补上：

```
🔗 便签关联自愈：修复 1 条
```

`/api/todos` 还 JOIN 出 `source` / `item_status` / `item_id`，前端拿 `item_status` 兜底对齐历史错位数据。

### 已完成默认折叠，但给 6 秒反悔窗口

已完成的不占主视线，收进一条 `已完成 N 条，点开查看` 的折叠条。

但「点完就消失」体验很差——点错了会以为删了。所以完成后的 **6 秒内卡片留在原位**（带绿边 + `撤销` 按钮），过期才收进折叠区：

```js
const freshDone = new Map();   // id -> 过期时间戳
const FRESH_MS = 6000;
```

改完后要**先 `paint()` 一次**让撤销按钮挂上去，再 `setTimeout` 到期重绘。少了这一步，卡片留着但按钮进不来。

### 操作走 `⋯`，不做长按

iPhone Safari 里长按会弹出复制/翻译菜单，极难用。所以所有操作统一收到右侧 `⋯` 的操作条：置顶 / 复制文字 / 改标题备注 / 删除，外加三个状态 chip 直接跳转。

同理，**点正文不算操作**——点 `.ni-body` 进就地编辑（textarea，回车保存、Esc 放弃）。长按在 iOS 上就是个雷，整个应用都不用它。

### 宽屏要收窄

便签是短文本，在 1440px 下 `.main` 给出 1162px 的卡片宽度，chip 和圆圈隔着一片空白，眼睛来回跳。所以宽屏锁 720px：

```css
@media (min-width: 900px) {
  .note-toolbar, .note-search, .note-quick, #nt-list { max-width: 720px; }
}
```

### 弹层支持 Esc

`sheet()` 原来只能点 X 或点遮罩关。桌面端点 X 离手太远，补了 Esc：

```js
onKey = (e) => {
  if (e.key !== 'Escape') return;
  const masks = document.querySelectorAll('.sheet-mask');
  if (masks[masks.length - 1] !== wrap) return;   // 只有最上层响应
  e.stopPropagation(); close();
};
```

注意 `onKey` 要先声明再被 `close()` 引用（`let onKey = null`），否则 `close` 里访问 const 会撞 TDZ。

## 二十一、全局搜索（首页顶部）

首页搜索框在问候卡下方，输入即搜（300ms 防抖），回车立刻搜。结果以**浮层**压在页面上，不再把首页往下顶。

### 两种模式，用户自己选

| 模式 | SQL | 语义 | 适合 |
|---|---|---|---|
| 模糊（默认） | `LIKE '%词%'` | 包含即命中 | 只记得大概 |
| 精准 | 词首命中 | 从头开始匹配 | 记得开头几个字 |

```js
const PUNCT = ['《', '「', '“', '（', '(', '：', ':', '·', '-', '—', '/', '、'];
```

## 二十二、回收站

对齐 Windows 11：删掉的东西先来这里，30 天内随时还原，超期自动彻底删除。

### 软删除 + 整行快照

`recycle` 表存 `(user_id, entity, entity_id, title, payload, deleted_at)`，`payload` 是**整行的 JSON 快照**。还原只需 `UPDATE ... SET deleted_at=NULL`；彻底删除后再撤销，靠 `payload` 原样 `INSERT` 回去（保留原 id），连实体行已被物理删掉也能整体复活。

```js
const RECYCLE_KEEP_DAYS = 30;
function purgeExpired(userId) { /* 每次打开回收站顺手清过期的 */ }
```

### 一律走 `recyclePut`，不许绕过

原来有四类删除**绕过**了回收站：

| 表 | 之前的症状 |
|---|---|
| `teachers` 教师名册 | **完全删不掉**，报「不支持的删除类型」 |
| `periods` 节次 | 同上 |
| `trip_items` 出差发票 | 删了就没了 |
| `attachments` 课件/原件/发票 | 删了就没了 |

前两个的根因是**路由注册顺序**：通用 `DELETE /api/:table/:id` 注册在前，专用 `DELETE /api/teachers/:id` 在后，通用那条永远先接住；而 `RECYCLE_TITLE` 白名单里没有 `teachers`，直接 `fail(400)` 掉。

现在抽成一个统一入口：

```js
const RECYCLE_TITLE = { /* 21 类，决定标题怎么生成，也决定哪张表能删 */ };
const RECYCLE_CASCADE = { attendance_tables: { table: 'attendance_rows', key: 'table_id' } };

function recyclePut(userId, table, id, extraTitle = '') {
  // 标删实体 → 写 recycle 快照 → 连带处理从表
}
```

`RECYCLE_CASCADE` 处理主从表：删考勤表时，明细行一起进回收站。

**头像是个例外**：换头像会顺手标删旧文件，那是内部清理，用户没删过东西，不该塞进回收站制造噪音。所以 `attachments` 按 `owner_type === 'avatar'` 分流。

### 撤销：三条彻底删除路径都要留快照

`purge` 接口返回 `undo` 快照数组，前端 8 秒内可点「撤销」整体复活。最初只有「清空回收站」留了快照，单条和批量彻底删除直接扔掉返回的 `undo`——删错了只能认。现在统一：

```js
const armUndo = (items, label = '已删除') => {
  undoBox = { items, label };
  clearTimeout(undoTimer);
  undoTimer = setTimeout(() => { undoBox = null; paint(); }, 8000);
};
```

> **注意**：撤销快照存在内存里，不落库。所以刷新页面就失效了——这是刻意的，8 秒的窗口不值得占数据库。过了 8 秒，东西是真的没了，确认弹层里也写清楚了「永久删除，无法恢复」。

### 过期清理

每次 `GET /api/recycle` 都先跑一次 `purgeExpired()`：把 `deleted_at < now - 30天` 的实体行物理删掉、`recycle` 行也删掉。不需要定时任务，用户不打开回收站就不清——反正也看不见。

### 手机上的两处细节

- 「全选 + 计数 + 排序」一行放不下，`.rec-tools > .btn` 要 `white-space: nowrap`，否则「全选」被挤成两行
- 排序 `<select>` 是 `.input`，自带 `width:100%`，光给 `flex: 0 0 auto` 会撑满整行，必须把宽度三件套都锁死：`flex-basis` / `min-width` / `max-width`

## 二十三、登录方式（密码 / 短信 / 微信 / QQ / WorkBuddy）

登录页底部有四个社交入口。**它们能不能用，取决于 `.env` 里有没有填对应凭证**，不是摆设也不是全都能用。

### 现状对照

| 入口 | 走什么协议 | 必需配置 | 没配时表现 |
|---|---|---|---|
| 密码登录 | 本站自建 | 无 | 始终可用（主力方式） |
| 验证码登录 | 短信通道 | `SMS_*` 任一组 | 该标签直接不显示 |
| 微信 / QQ | OAuth 扫码 | `WX_APPID` / `QQ_APPID` | 提示「尚未开通」 |
| WorkBuddy | OAuth 2.1 跳转授权 | `WORKBUDDY_CLIENT_ID/SECRET` | 提示「未开通」 |

前端的判断依据是 `GET /api/auth/config` 返回的两个开关：

```js
qrEnabled: !!(CONFIG.wxAppId || CONFIG.qqAppId),          // 有真二维码可扫
wbEnabled: !!(CONFIG.workbuddyClientId && CONFIG.workbuddyClientSecret),  // 跳转登录可用
```

`workbuddyClientId` **不算进 `qrEnabled`**。这点是踩过坑的：WorkBuddy 走的是整页跳转授权，根本不扫码，把它算进扫码能力里，会导致「有二维码但扫了没反应」。

### 一个必须记住的坑：二维码曾经是画出来的

`drawQR()` 用 FNV 哈希 + xorshift 生成伪随机图案，渲成 SVG。它长得像二维码，**但任何手机扫上去都不会有反应**——因为它根本不是按 QR 编码规则生成的。

原来的逻辑是：点 WorkBuddy → 接口报 `notConfigured` → **fallback 到这张假二维码**。用户看到「二维码加载中…」然后「等待扫码…」，扫半天没反应，还以为是自己手机的问题。

现在改成：没配置就明说没配置，不再拿假图案糊弄人。`authQr()` 分三种情况渲染：

```js
if (!AUTH_CFG.qrEnabled) {
  // 明确告知未开通，不再渲染任何二维码
  // 若 wbEnabled，给一个「改用 WorkBuddy 登录」的按钮
  return;
}
```

### WorkBuddy 接入（OAuth 2.1 授权码流程）

流程五步，全在服务端：

```
① GET  /api/auth/workbuddy/start      生成 state 落库 → 返回授权 URL
② 浏览器 302 到 workbuddy.cn/openapi/v2/authorize（用户在那里登录并同意）
③ workbuddy.cn 带 ?code=&state= 跳回 /api/auth/workbuddy/callback
④ 服务端用 code + client_secret 换 access_token（POST /openapi/v2/token）
⑤ 用 token 拉昵称头像 → 建/找本地账号 → 种 Cookie → 302 回 /?wb_login=1#/home
```

**四个必须踩准的点：**

1. **`redirect_uri` 要字节级一致**。授权阶段和换 token 阶段传的必须完全相同（含结尾斜杠与否）。所以统一走 `wbRedirectUri()` 生成，不手拼。线上反向代理后 `req` 拿到的是内网地址，所以优先读 `X-Forwarded-Proto/Host`，或直接在 `.env` 里写死 `WORKBUDDY_REDIRECT_URI`。

2. **`state` 落库不落内存**。用户可能在授权页停留几十秒，服务也可能重启。只存内存会在回调时找不到记录，报一个莫名其妙的「state 不匹配」。表 `oauth_states` 带 `expires_at`，10 分钟过期，每次 `/start` 顺手 `gcOauthStates()` 清过期的。

3. **state 一次性消费**。回调进来不管成功失败，先 `DELETE FROM oauth_states` 再判断。否则同一个 state 可以被重放。

4. **回调跳转必须是 `/?参数#/home` 而不是 `/#参数`**。本站是 hash 路由，放在 `#` 后面的东西前端用 `location.search` 永远读不到——提示就永远不出现。踩过这个坑。

```js
function wbFailPage(res, msg) {
  res.writeHead(302, { Location: `/?wb_error=${encodeURIComponent(msg)}#/home` });
  res.end();
}
```

### ALLOW_REGISTER=0 不该拦 OAuth 用户

`ALLOW_REGISTER=0` 是「不许陌生人凭空注册」，拦的是自助注册。OAuth 登录的用户已经过 WorkBuddy 实名授权，属于可信来源，首次登录时自动建账号是对的。这条规则只作用于 `/api/auth/register`，不影响 OAuth 首次建号。

### 绑定与解绑

「我的 → 账号与绑定」里 WorkBuddy 那一行，原来按钮是 `disabled` 的，点了只弹「需配置开放平台凭证」。现在能真正发起绑定：`purpose=bind` 存进 state，回调时看到 `st.user_id` 非空，就走绑定分支而不是新建账号。

解绑有个必须的护栏：**不能把自己最后一把钥匙扔掉**。

```js
if (!u.phone && !u.wx_openid && !u.qq_openid) fail(400, '请先绑定手机号或微信，再解绑 WorkBuddy');
```

### 回调提示怎么回显

回调是整页跳转，页面整个重载，提示只能靠 URL 参数。`main.js` 里 `handleWbCallback()` 认三个参数，弹完立刻 `history.replaceState` 把参数抹掉——否则用户刷新一次就再弹一遍。

| 参数 | 含义 | 提示 |
|---|---|---|
| `wb_login=1` | 登录成功 | 绿色 toast |
| `wb_bound=1` | 绑定成功 | 绿色 toast |
| `wb_error=` | 失败原因（URL 编码） | 红色 toast，显示原文 |

**参数必须放 `?` 不能放 `#`。** 第一版 `wbFailPage()` 写成了 `/?wb_error=xxx`，看着像带了参数，但前端是从 `location.search` 读的，而 hash 里的内容根本不会进 query。结果就是失败时静默回首页，用户完全不知道发生了什么。改成 `/?wb_error=xxx#/home` 才对——`?` 在前给前端读，`#` 在后给 SPA 定位。

### 上线必做三步

1. 去 <https://open.workbuddy.cn> 注册开发者账号，创建一个「Buddy 应用」
2. 在应用设置里登记 OAuth 回调地址：`https://你的域名/api/auth/workbuddy/callback`
3. 把 `client_id` / `client_secret` 填进 `.env`，同时写上 `WORKBUDDY_REDIRECT_URI`（**和登记的一字不差**），重启服务

`WORKBUDDY_REDIRECT_URI` 建议显式写死。虽然代码会从 `X-Forwarded-Host` 自动推断，但线上反向代理的转发头不一定完整，推断错了会得到一个浏览器打不开的回调地址——而 WorkBuddy 那边只认登记过的地址，对不上就直接拒绝。

### 授权范围

只申请了 `user.profile.readable`，够取昵称和头像。没有申请 `user.task.*`、`user.localassistant.*` 这些——工作台只需要知道「你是谁」，不需要碰你 WorkBuddy 里的任务和助理。scope 收得越窄，出问题时的爆炸半径越小。

## 二十四、`[hidden]` 被 CSS 覆盖的那个坑

**现象**：首页搜索框下面凭空多出一条 560×22 的白色圆角空条，横在页面中间，看着像排版崩了。截图里被红框圈出来的就是它。

**根因**：搜索结果的浮层是这么写的——

```html
<div class="sr-panel" id="search-result" hidden></div>
```

```css
.sr-panel { display: flex; ... }
```

`hidden` 属性在浏览器默认样式表里对应 `[hidden] { display: none }`，优先级是**一个属性选择器**。而 `.sr-panel` 是**一个类选择器**，两者特异性相同，但作者样式表优先于浏览器默认样式表——于是 `display: flex` 赢了，元素标记着 `hidden` 却照样渲染出来。

它 `position: fixed; top: 50%`，所以不占文档流，只是凭空浮在屏幕正中，宽 `min(560px, 100vw-24px)`、内容为空所以只有 `padding` 撑出来的 22px 高。肉眼看到的就是一条白色圆角空心条。

**修法**：给 `[hidden]` 显式兜底，且用 `!important` 压住后续任何 `display` 声明。

```css
.sr-panel[hidden], .sr-scrim[hidden] { display: none !important; }
```

`.sr-scrim` 当时没出问题，是因为它没写 `display`，默认 `block`——但这是运气，不是设计。一并补上，以后谁给它加 `display: flex` 也不会翻车。

### 怎么自查同类问题

不要只盯着代码看，直接在浏览器里扫一遍：

```js
[...document.querySelectorAll('[hidden]')]
  .filter(e => {
    const s = getComputedStyle(e), r = e.getBoundingClientRect();
    return s.display !== 'none' && r.width > 0 && r.height > 0;
  })
```

只要返回非空，就是有元素「说好了隐藏、实际还占着地方」。这个检查已经加进回归脚本，六个路由 × 三端全部扫过一遍。

> **经验**：凡是给容器写了 `display: flex / grid`，同时又用 `hidden` 属性控制显隐的，都必须补一条 `[hidden] { display: none }`。这类 bug 不会报错、不会崩，只是默默多出一块谁也说不清是什么的东西——最难查。

## 二十五、天气城市：从「自动定位」改成「手动选城市」

**改之前**：进首页就调 `navigator.geolocation.getCurrentPosition()`。桌面浏览器一律弹授权框，用户点「拒绝」还要再吃一个红色的「定位失败：User denied Geolocation」提示。等于每开一次页面先添一次堵，而天气还没看到。

**改之后**：定位从「默认动作」降级成「可选动作」。

| 位置 | 之前 | 现在 |
|---|---|---|
| 天气卡按钮 | `定位` | `选城市` |
| 面板标题 | `选择城市 / 定位` | `选择所在城市` |
| 面板第一屏 | 「使用当前定位」按钮 + 城市列表 | **城市列表**（48 个，当前城市高亮） |
| 定位入口 | 面板顶部，主推 | 挪到列表下方，可选 |
| 进首页行为 | 自动申请定位权限 | 不申请，直接用上次选的城市 |

默认城市是北京，选过一次就记住（`localStorage` 的 `city`），之后永远不用再选。

### 为什么要这么改

天气这种信息，**「上次选的城市」比「这次定位的位置」更符合预期**。人在办公室查天气，和在通勤路上查天气，想看的是同一个地方。自动定位反而会在你出差时把天气悄悄换掉，还得再改回来。

而且定位授权一旦被拒，浏览器会记住这个决定，再调也不弹框了——用户连「重新允许」的入口都找不到，只剩一个报错的 toast。

### 代码上的三处

```js
// 1. 首页不再自动定位（整段调用删掉，只留注释说明原因）
registerView(async function home(main) {
  clearInterval(clockTimer);
  main.innerHTML = `...`;
  // 不再自动申请定位权限 ...
  try { await loadWeather(); } catch (e) { /* 离线降级 */ }

// 2. geoMode 默认值 auto → manual
geoMode: ls.get('geoMode', 'manual'),

// 3. 面板重排：列表在前，定位在后；当前城市加 .on 高亮
const cur = state.city?.name || '';
return `<button class="chip-btn${on ? ' on' : ''}" data-c="...">...</button>`;
```

`.chip-btn.on` 这个样式本来就有（`background: var(--primary); color: #fff`），复用现成的，不用新增 CSS。

> **一个判断标准**：凡是「自动做某件事」的功能，先问它在失败时会不会打扰用户。定位、通知、摄像头这类需要授权的能力，失败是常态而非例外——默认关掉，把开关交给用户，体验会好很多。

## 二十六、定位显示的永远是 "Shanghai"

**现象**：点「用当前位置定位」，天气卡的城市变成 `Shanghai`。人明明在北京、成都、广州，结果都是 Shanghai。

**根因**：所谓的「反查地名」根本没查地名。

```js
// 旧代码：拿经纬度去问天气接口，再从时区字段里截最后一段
async function reverseGeocode(lat, lon) {
  const r = await fetch(`https://api.open-meteo.com/v1/forecast?latitude=${lat}&longitude=${lon}&current=temperature_2m&timezone=auto`);
  return r?.timezone?.split('/').pop()?.replace(/_/g, ' ') || '当前位置';
}
```

`timezone` 返回的是 `Asia/Shanghai`，`split('/').pop()` 得到 `Shanghai`。

**问题在于：整个中国大陆共用同一个 IANA 时区 `Asia/Shanghai`。** 无论人在漠河还是三亚，时区都是它。所以这段代码的返回值恒等于「Shanghai」，跟实际位置毫无关系——但它看起来特别像是对的：定位成功了、城市名显示了、天气也换了，只有名字是错的。

> 这类 bug 最阴的地方在于**它不报错、不异常、界面还"正常"**。用户以为定位不准，实际是名字压根没查过，而天气用的却是真实 GPS 坐标（所以温度是对的，只有地名错）。两个数据来自不同来源，一个真一个假。

**修法**：换成真正的反向地理编码服务。用 BigDataCloud 的免费接口（无需 key，支持 `localityLanguage=zh`）。

```js
const r = await fetch(
  `https://api.bigdatacloud.net/data/reverse-geocode-client?latitude=${lat}&longitude=${lon}&localityLanguage=zh`,
  { signal: AbortSignal.timeout(7000) },
);
const trim = (s) => String(s || '').replace(/市$/, '').trim();   // 「北京市」→「北京」
const city = trim(r?.city);
if (city) return city;
const prov = trim(r?.principalSubdivision);                       // city 为空时退到省
if (prov) return prov;
return `${lat.toFixed(2)}, ${lon.toFixed(2)}`;                    // 查不到就照实报坐标，不编城市名
```

实测四个城市：北京→北京市、上海→上海市、广州→广州市、成都→成都市、哈尔滨→哈尔滨市，`city` 字段全部准确。

### 反过来吸附到城市表

反查到名字后，如果这个名字在 48 个常用城市里，就用表里的市中心坐标替换 GPS 原始坐标：

```js
const hit = CITIES.find((c) => c[0] === name);
state.city = hit ? { name: hit[0], lat: hit[1], lon: hit[2] } : { name, lat: latitude, lon: longitude };
```

理由：天气按行政区算，差几百米结果一样，但「北京」比「39.90, 116.41」好看得多，也能让城市列表里的高亮对上。

### 顺带一个 `const` 的坑

`locate()` 里用到 `CITIES`，但 `CITIES` 定义在文件更靠后的位置。函数调用发生在定义之后，所以实际不会报错——但这是**运行时才安全**，属于隐患：哪天有人在模块顶层调用 `locate()`，立刻 `ReferenceError: Cannot access 'CITIES' before initialization`。已经把 `CITIES` 挪到 `reverseGeocode` / `locate` 之前。

### 坐标输入框撑破面板

`.input` 自带 `width: 100%`，两个框都写 `flex: 1`，等于「各自都要占满一行」，把面板撑破。

```css
/* 错 */ style="flex:1"
/* 对 */ style="flex:1 1 0;width:0;min-width:0"
```

`width: 0` 是关键——`flex-basis` 会覆盖 `width`，但 `min-width: auto` 默认不允许收缩到内容宽度以下，所以三个都得写。这和回收站排序框那次是同一类问题，`.input` 的 `width: 100%` 是个反复惹事的默认值。

## 二十七、城市改成「按名字搜」，经纬度收进折叠区

### 问题

面板里给两个输入框「纬度 / 经度」，用户原话：

> 输入的时候最好是输入所在的城市，而不是经纬度，我根本不知道当前的经纬度是多少。

这是设计错误，不是 bug。没有任何普通用户知道自己脚下的经纬度，让人填坐标等于把人挡在门外。内置 `CITIES` 只有 48 个常用城市，列表点选也只能覆盖这些，全国几百个地级市点不到。

### 做法

面板第一行换成城市名输入框，输入即搜；经纬度收进 `<details>` 折叠区，默认不展开。

数据源用 Open-Meteo 自带的地理编码接口：

```
https://geocoding-api.open-meteo.com/v1/search?name=荆州&count=10&language=zh&format=json
```

选它有两个理由：**和天气接口同一个域名**（`api.open-meteo.com` vs `geocoding-api.open-meteo.com`，同源策略下不额外触发预检），以及免费无 key。

### 这个接口的中文数据有三个坑

实测出来的，不处理就会给出错误城市：

| 坑 | 现象 | 处理 |
|---|---|---|
| 查不到不带「市」的地级市 | 搜「荆州」返回空，搜「荆州市」才有（湖北 30.35,112.19） | 自动再补一轮「关键词 + 市」 |
| 同名小地方排在真城市前面 | 搜「周口」返回四川/广西/河南三个村，真正的地级市没进前列 | 按 `feature_code` 排序：`PPLC` → `PPLA` → `PPLA2` → `PPL`，同级再按人口降序 |
| 混进机场等设施 | 搜「鄂尔多斯」会带出「鄂尔多斯伊金霍洛机场」 | 黑名单过滤 `AIRP`/`ADM1~4`/`PPLX`/`HSP` |

排序修正后实测：

| 输入 | 返回 | 首条是否为用户想要的那个 |
|---|---|---|
| 荆州 | 1 条 | ✅ 荆州 湖北 |
| 周口 | 3 条 | ✅ 周口 河南 |
| 鞍山 | 6 条 | ✅ 鞍山 辽宁 |
| 丽水 | 1 条 | ✅ 丽水 浙江 |
| 喀什 | 1 条 | ✅ 喀什 新疆 |
| 鄂尔多斯 | 1 条 | ✅ 鄂尔多斯 内蒙古（机场已滤掉） |

### 防抖与竞态

打字每敲一下就发请求既浪费也会乱序：先发的请求可能后回来，出现「输入荆州、列表显示周口」。两个措施：

```js
let timer = 0; let seq = 0;              // 350ms 防抖 + 递增序号
const my = ++seq;
const rows = await geocodeCity(q);
if (my !== seq) return;                  // 过期响应直接丢掉
```

回车不提交表单，直接取第一条结果并切换，省一次点击。

### 顺带清掉的过时文案

同一处还挂着「手机允许定位权限后，打开首页会自动定位」——自动定位在上一轮就删了（见第二十五节），文案没跟着改。改成「需要允许浏览器的定位权限」。**删功能时记得搜一遍文案**，这种谎话比没有说明更糟。

## 二十八、「常用城市」改成「最近使用」，砍掉经纬度输入

用户看过第二十七节的效果后给的两条意见：

> 常用城市显示用户自己最近定位的五个城市，其他的全部去掉。手动输入经纬度去掉。

### 为什么原来那 48 个城市是错的

它们叫「常用城市」，但常用的人是我（写代码的人）猜的，不是用户自己用出来的。人在荆州，一屏全是北上广深，二十多个按钮里没有一个能用的。**凡是「猜出来的常用」，多半都不常用。**

改成记录用户实际用过的：

```js
const RECENT_MAX = 5;
function recentCities() {          // 读，最多 5 条
  const a = ls.get('recentCities', []);
  return Array.isArray(a) ? a.filter(c => c && c.name && c.lat != null).slice(0, RECENT_MAX) : [];
}
function pushRecentCity(c) {       // 写：同名去重 → 插到队首 → 截断到 5
  const rest = recentCities().filter(x => x.name !== c.name);
  const next = [{ name: c.name, lat: c.lat, lon: c.lon }, ...rest].slice(0, RECENT_MAX);
  ls.set('recentCities', next);
  return next;
}
```

去重时是「先删同名、再插队首」而不是「插队首后去重」——顺序反了会保留旧的、把刚切的丢掉。

两个写入点：`commit()`（搜索选中或点最近项切换）和 `locate()`（定位成功）。定位本来也应该算「用过的城市」，不然定位到荆州、下次还得重新搜。

### 空状态

新用户一条记录都没有，标题「最近使用」下面空着会很难看。没有记录时整块 `hidden`，连标题一起藏掉。搜索时也藏起来，把屏幕让给结果；清空搜索框再恢复。

### 经纬度输入整块删除

`<details>` 折叠区连同 `#lat`/`#lon`/`#use-coord` 全部删掉。上一轮把它折叠起来只是眼不见，这次直接去掉——留一个没人会展开的入口只是噪音。`locate()` 里对 `CITIES` 的吸附逻辑一并删除，定位直接用 GPS 原始坐标（天气接口本来就按坐标算，比吸附到市中心更准）。

### 验证

| 场景 | 结果 |
|---|---|
| 首次打开（无记录） | 最近区块隐藏，坐标输入框数量 0 |
| 依次切 6 个城市 | 只剩 5 个，最新的在最前：`鄂尔多斯, 喀什, 丽水, 鞍山, 周口` |
| 点最右边那个老城市 | 顶到队首、不重复：`周口, 鄂尔多斯, 喀什, 丽水, 鞍山` |
| 输入关键词 | 最近区块隐藏；清空后恢复显示 |
| 三端布局 | 手机 390 / iPad 640 / 桌面 480，均无横向溢出，面板高度大幅缩短 |

面板高度从原来塞满 48 个城市的一屏多，缩到现在四五个胶囊 + 一行定位按钮。

## 二十九、搜索结果一次全部铺开

用户截图圈出搜索面板右上角的「模糊 / 精准」，要求「搜索时直接展示全部的搜索结果就行」。

### 原来卡在哪

两处截断叠在一起：

| 层 | 原限制 | 结果 |
|---|---|---|
| 前端 `SR_LIMIT` | 每组只渲染前 5 条，其余藏在「展开其余 N 条」按钮后 | 搜「教学」看到 4 条课表，实际有 17 条 |
| 服务端 SQL | 每张表 `LIMIT 30` | 教师名册 146 人，搜「张」最多只回来 30 个 |

只改前端没用——前端全展开也只是把 30 条摆出来；只改服务端也没用——多出来的还是折在按钮后面。

### 改法

- 删掉 `SR_LIMIT`、`srOpen` 状态、`[data-more]` / `[data-less]` 的绑定与按钮模板，直接 `g.rows.map(...)` 全量渲染；
- 服务端 15 处 `LIMIT 30` 统一改成 `LIMIT 500`。

保留 500 而不是彻底不设限：搜索是「输入即查」，不设上限时搜一个「的」字会把全库捞出来拼成几 MB 的 JSON，手机端直接卡死。500 条对一个单人工作台等于「全部」，同时兜住了异常输入的底。

### 关于「模糊 / 精准」

这两个不是结果筛选，是**匹配方式**：模糊 = 包含即命中，精准 = 从词首开始匹配。用户说的「展示全部」指的是不要折叠，不是要取消匹配模式，所以这个切换保留。

### 验证

| 关键词 | 头部总数 | 实际渲染行 | 展开按钮 |
|---|---|---|---|
| 教学 | 20 | 20（笔记 1 + 事项 1 + 课表 17 + 监考 1） | 0 |
| 张 | 17 | 17（教师名册 14 + 学生名册 2 + 监考 1） | 0 |

手机 390 / 桌面 1440 两端均无横向溢出、无 JS 报错，`.sr-body` 自身 `overflow-y:auto` 滚动正常。

## 三十、删掉「加到系统日历」，提醒只在本页面响

## 三十一、恢复「加到系统日历」，这次走对了路

第三十节把 `.ics` 导出删掉了，理由是"手机上点了没反应"。**这个判断是错的**，用户当场纠正：

> 加到系统日历应该是调用当前系统的日历。

查证后确认：iOS 的 Safari 认得 `text/calendar` 这个 MIME，收到就会把文件交给「日历」App，日历弹出带「添加」按钮的预览页——这正是想要的效果。之前失败不是因为做不到，是因为**实现方式不对**。

### 三个关键修正

**1. 不能用 blob URL，要用 http 地址**

```js
// 错：blob 不走 Safari 的「按 MIME 交给对应 App」那一步
const url = URL.createObjectURL(new Blob([ics], { type: 'text/calendar' }));

// 对：http(s) 地址 + 正确的 Content-Type
res.writeHead(200, { 'Content-Type': 'text/calendar; charset=utf-8' });
```

所以改成服务端出文件：前端 `POST` 内容 → 服务端存库发一张取件码 → 前端拿 `/api/calendar/ics/<code>` 去下载。

**2. 内容存服务端，不编进 URL**

标题里有中文和标点，塞进 query string 会被微信这类内置浏览器重新编码（查证时看到有案例是 query 被改写导致参数丢失），轻则乱码重则整条丢。取件码是 128 位随机串，10 分钟过期，`calendar_exports` 表存内容。

交付接口**故意不带登录校验**：Safari 把请求转交日历 App 时不保证还带着 Cookie，挂鉴权就会 401。安全性由随机码 + 短过期兜住。

**3. 识别三种会失败的环境，别让用户对着没反应的按钮发呆**

| 环境 | 表现 | 处理 |
|---|---|---|
| 微信/QQ/钉钉内置浏览器 | WKWebView 拿到文件无处可去，静默丢弃 | 识别 UA，提示「点右上角 … 选『在 Safari 中打开』」 |
| 加到主屏幕（standalone） | 脱离 Safari 文件处理链，下载被拦 | 改用 `window.open` 让 Safari 接管 |
| 安卓 | 能下载但要手动用日历打开 | `window.open` + 提示「用手机自带日历打开」 |

普通 Safari 标签页走 `<a download>`，不跳走当前页面。

### 恢复的四处入口

| 位置 | 按钮 |
|---|---|
| 闹钟弹层 | 「加到系统日历」，点了不关弹层（用户回来还要点「知道了」） |
| 倒数卡片（有安排 / 无安排两个分支都加） | 「日历」，导出全部 `scheduled` 状态的提醒 |
| 新建提醒面板 | 「加到系统日历」，只进日历不建应用内提醒 |

### 排查中踩的四个坑（都值得记）

1. **裸 `fetch` 漏了 `credentials: 'same-origin'`** —— 项目里其他请求都走 `api()` 封装（自带这个参数），这里手写的 fetch 没有，结果接口 200、前端拿不到。表现是函数静默返回 `false`，没有任何报错。
2. **取错了响应层级** —— 接口统一包了一层 `{ok, data}`，我写成 `r.url` 应该是 `r.data.url`。同样静默失败。
3. **测试数据不满足前置条件** —— `exportCalendar` 只导出 `status='scheduled'` 的提醒，而我库里那几条全是 `fired`/`acked`，于是每次都在「还没有待触发的提醒」处 return。**测功能前先确认数据满足条件**，别急着怀疑代码。
4. **监听器挂载方式不对** —— 用 `MutationObserver` 抓 `<a>` 时因为元素插入后立刻 `remove()`，抓到 0 条，一度误判成"没执行到"。改成钩 `HTMLAnchorElement.prototype.click` 才看清。

### 验证

|---|---|
| `POST /api/calendar/ics` | 200，返回取件 URL |
| `GET /api/calendar/ics/<code>` | 200，`Content-Type: text/calendar; charset=utf-8` |

### 一个不容易发现的定位 bug

写完样式在 iPad 尺寸下一测，面板跑到屏幕下半截、底部超出视口约 300px。

一开始怀疑是 `transform` 或 `backdrop-filter` 造出了新的包含块，把 `.sr-panel` 到 `<body>` 的祖先链和它们的 `position / transform / filter / will-change / contain` 全打出来看，**全是 static 和 none**，找不到元凶。

关键线索是 `getComputedStyle(el).top` 返回的是 `590px`——而 CSS 里写的是 `top: 50%`。百分比被算成了像素，说明**浏览器压根没把它当定位元素**。往上翻样式表，发现 `.sr-panel` 的主规则里确实没写 `position`。

那之前为什么看着是居中的？因为 `.sr-scrim`（铺满全屏、`position: fixed`）正好是它前面一个兄弟节点，把面板顺理成章地顶到了第二屏的位置。**视觉上像居中，实际上纯属巧合**，一换屏幕高度就露馅。

```css
/* 错的：没写 position，top: 50% 相对静态包含块算，等于没用 */
.sr-panel { z-index: 61; left: 50%; transform: translateX(-50%); top: 50%; }

/* 对的 */
.sr-panel { position: fixed; ... }
```

还有一处是 `1fr` 高度的 flex 容器在 `max-height` 下不去撑满，导致纵向居中又偏了几像素，换成 `margin-top: calc(-1 * min(44vh, 450px))` 直接刚性偏移，任何尺寸下都是精确居中。

教训：**`position: fixed` 的居中，先确认它真的是 fixed。** 看到 `getComputedStyle` 返回的百分比变成了像素值，就是定位没生效的信号。

## 三十三、整份数据莫名翻倍：一次 seed 防重复失效的事故

### 现象

搜索结果里每条都出现两遍，搜「教学」返回 40 条而不是 20 条。顺手扫了整个库，发现不是只有搜索：

| 表 | 正常 | 事故时 |
|---|---|---|
| periods（节次） | 10 | 30 |
| courses（课表） | 17 | 51 |
| students（学生） | 78 | 234 |
| items / todos / notes | 5 / 4 / 4 | 10 / 8 / 8 |
| categories / punishments / materials | 13 / 22 / 3 | 26 / 44 / 9 |

19 张表里 16 张翻倍，共多出 **182 行**。备份文件从 39KB 涨到 71KB，正好对得上。

### 定位过程

1. 对比 `backups/` 里全部 11 份备份的逐表行数——**14:18 那份还是干净的，14:33 那份已经翻倍**。中间只发生过「发布上线」这一件事。
2. 看发布脚本，它只做 `createArtifactRelease`，不碰数据库。那问题只能是**重启时跑出来的**。
3. 重启时会执行 `seedUserData()`，它开头有一道防重复检查：

```js
// 有问题的那行
const has = one('SELECT COUNT(*) c FROM periods WHERE user_id=?', userId)?.c || 0;
if (has > 0) return;
```

4. 查 `periods` 表：`user_id=1` 有 10 行，`user_id=2` 有 10 行，**而 `users` 表里只有 id=1**。也就是说 `user_id=2` 是个已经不存在的用户留下的孤儿数据。
5. 关键：翻倍后 `periods` 里出现了 30 行——`user_id=1` 占了 20 行。可是这道检查明明查的就是 `user_id=1`、明明有数据，为什么会灌？

答案在 id 分布上。翻倍产生的新行不是递增到表尾，而是**补进了中间的断档**（`items` 从 `1~5` 跳到 `31~35`，`todos` 从 `1~4` 跳到 `38~41`，`trip_items` 的 `5` 号位被占了）。这是 SQLite 对 `INTEGER PRIMARY KEY` 在没写 `AUTOINCREMENT` 时的标准行为——取 `max(id)+1`，表被清过就会填回空位。

顺着这条线翻出一个更早的动作：`user_id=2` 的数据是「清空了内容、但序列没跟着归位」留下的。那次清空之后 `periods` 表里只剩 `user_id=2` 的 10 行，`user_id=1` 一行不剩，于是 `seedUserData(1)` 的检查读数为 0，**每次重启都判一次「没灌过」，再灌一遍**。

### 修复

```js
/* 多表连查：只要这个用户名下有任何一份种子数据，就认定灌过了。
   单看 periods 一张表，一旦这张表恰好没有该 userId 的行，就会天天重灌。 */
const probes = [
  'SELECT COUNT(*) c FROM periods WHERE user_id=?',
  'SELECT COUNT(*) c FROM courses WHERE user_id=?',
  'SELECT COUNT(*) c FROM students WHERE user_id=?',
  'SELECT COUNT(*) c FROM categories WHERE user_id=?',
];
for (const sql of probes) {
  try {
    if ((one(sql, userId)?.c || 0) > 0) return;
  } catch { /* 表不存在就当这条不适用 */ }
}
```

### 数据清理

删哪一份不用猜：id 小的那份是第一次灌的，id 大的那批和用户自己录的数据是同一轮分配的。**保留 id 小的，删掉 id 大的。**

前提是逐组核对——除 `id / created_at / updated_at` 外所有字段必须完全一致。实际跑下来有 2 组不一致，差异都只在 `deleted_at` 上：

| 组 | 情况 |
|---|---|
| `trips` 4 / 8 | 4 是正常记录，8 有删除标记 |
| `trip_items` 4 / 6 | 4 有删除标记，6 是删除后又插入的 |

这两组要留**有删除标记**的那份——用户是自己删的，不能给他复活回来。

清理脚本的做法：

1. 逐字段比对，只处理完全一致的组，不一致的单独报出来人工看
2. 删之前把待删行完整导出成 JSON 快照
3. 一个事务内删除，出错整体回滚
4. 删完把 `sqlite_sequence` 拉回当前最大 id，否则下次插入会从空出来的大号继续跳

### 顺带清掉的两类垃圾

- **孤儿数据**：`user_id=2` 的 109 行（节次 10、课表 17、学生 78、教材 3、短链 1、出差 1），这个用户根本不存在
- **测试误录**：线上点课表格子时手滑新增的一条 `class_name='6'` 的课（`created_at` 就是测试当时那一分钟）。教训是**点格子的测试要放到最后，或者点完立刻删掉**

### 验证

| 检查项 | 结果 |
|---|---|
| 全库重复扫描（30 张表） | 0 组重复 |
| 重启后是否再翻倍 | 未再增长 |
| 搜「教学」 | 本地 20 条、线上 20 条（修复前 40 条） |
| 课表 | 17 节，班级为高二(3)班 / 高二(5)班 |
| 备份体积 | 71KB → 39KB |
| 备份内容 | 与修复后的库一致 |
| 清理快照 | `backups/_dupfix/`（含删除前整库 + 待删行 JSON） |

### 教训

**防重复的检查不能只盯一张表。** 只要那张表恰好缺了这个 userId 的行，检查就形同虚设，而且失效时不会报错，只会安静地多灌一份。这类检查本质上是「这个用户有没有被初始化过」，判断依据应该覆盖多张主表，而不是挑其中一张当代表。

### 1. 点「全部已读」后，左侧「我的」上的红点不消失

**现象**：消息中心点「全部已读」，列表清了，但左边导航「我的」上的角标还挂着。

**根因有两层，只修第一层是不够的**：

- 第一层：「全部已读」只重绘了消息列表，没有重新拉未读数、也没动导航。补 `refreshUnread() + paintUnread()`。
- 第二层（更隐蔽）：`navHTML` 里角标是这样渲染的——

  ```js
  const badge = n.id === 'me' && state.unread ? `<span class="badge-dot">…</span>` : '';
  ```

  也就是说**未读数从 0 变成有新消息时，页面上根本没有这个节点**。而 `paintUnread` 原本只做 `querySelectorAll('.badge-dot')` 改 `textContent`，没有节点就等于改空气。
  所以「点了全部已读不消失」和「来了新消息角标不出现」是同一个 bug 的两个方向。

**改法**（`public/js/ui.js`）：`paintUnread` 改成遍历 `[data-nav=me]`，没有节点就创建一个，归零就隐藏。

```js
export function paintUnread() {
  const n = Number(state.unread) || 0;
  document.querySelectorAll('[data-nav=me]').forEach((nav) => {
    let dot = nav.querySelector('.badge-dot');
    if (n <= 0) { if (dot) dot.hidden = true; return; }
    if (!dot) { dot = document.createElement('span'); dot.className = 'badge-dot'; nav.appendChild(dot); }
    dot.textContent = n > 99 ? '99+' : String(n);
    dot.hidden = false;
  });
}
```

**验证**：库里插 3 条未读 → 页面角标显示 `3` → 点「全部已读」→ `hidden=true`。

### 2. 头像「移除」点确认没反应

**现象**：头像弹窗点「移除头像」→ 确认 → 什么都没有。

**根因（两个都在，叠在一起）**：

- **`confirmDialog` 的 Promise 竞态**：`sheet` 的 `onClose` 会 `resolve(false)`，而确认分支是 `resolve(true)` + 直接 `s.wrap.remove()`。`closed` 标记没同步，或者用户点完立刻按 Esc / 点遮罩，先走 `onClose` 就把 Promise 定成 `false` 了。
  改法：两个对话框都加 `settled` 一次性闸门，`done()` 只让第一次生效，且统一走 `s.close()`。
- **服务端路由被通配路由截胡**（这个更关键，光修前端还是会失败）：

  ```
  route('DELETE', '/api/:table/:id', …)   // 第 1299 行注册
  route('DELETE', '/api/me/avatar', …)    // 第 2339 行注册
  ```

  分发是 `routes.find(r => r.method === m && r.re.test(p))`，**按注册顺序取第一个匹配**。于是 `DELETE /api/me/avatar` 先撞上通配那条，被当成「删 `me` 表里 id 叫 `avatar` 的行」，回 `400 不支持的删除类型`。
  前端表现就是「点了确认，什么也没发生」——只弹了个 2.4 秒就消失的 toast，还被后续提示盖住了。

**改法（根治，不是打补丁）**：`server/index.mjs` 里给 `route()` 记下每个模式「写死的字符数」，分发时取最具体的那条：

```js
const literal = pattern.replace(/:[A-Za-z_]+/g, '').length;

function pickRoute(method, pathname) {
  let best = null;
  for (const r of routes) {
    if (r.method !== method || !r.re.test(pathname)) continue;
    if (!best) { best = r; continue; }
    if (r.literal > best.literal) { best = r; continue; }
    if (r.literal === best.literal && r.keys.length < best.keys.length) best = r;
  }
  return best;
}
```

`/api/me/avatar` 的 `literal` 是 14，`/api/:table/:id` 是 8，前者胜出。这样以后再加接口不会重复踩同一个坑。

顺带确认：`/api/teachers/:id`、`/api/attachments/:id` 之前也是被截胡的，这次一起修好了。

**回归**：`GET /me`、`/me/sessions`、`/messages`、`/preps`、`/lessons/summary`、`/teachers`、`/attachments`、`/courses` 全部 200，无回归。

### 5. 首页欢迎语「每次进来都不一样」

**现象**：同一个上午刷新几次，能看到「上午好」和「下午好」两种，像坏了。

**根因**：问候语是按「每分钟随机挑一条」实现的（`Math.floor(Date.now()/60000)` 做种），7 条候选里上午可能挑到下午那句。

**改法**：按时段硬绑定，改成 7 档起始小时表，几点就是哪一句，一天内不会变：

```js
const GREETS = [
  [5,  '早安，{name}。',   '新的一天，先看清时间，再安排节奏。'],
  [9,  '上午好，{name}。', '把最重要的一件事放在今天的前两个小时。'],
  [12, '中午好，{name}。', '吃完再歇一会儿，下午的课才有力气。'],
  [14, '下午好，{name}。', '还有半天，够把一件难事推进一大步。'],
  [18, '傍晚好，{name}。', '今天该收尾的，别拖到明天。'],
  [20, '晚上好，{name}。', '晚自习的灯亮着，你也辛苦了。'],
  [23, '夜深了，{name}。', '明天的事，交给明天的你，今晚早点休息。'],
];
function greetFor(name) {
  const h = new Date().getHours();
  let cur = GREETS[6];                       // 0–5 点属于「夜深」，跨零点不跳回「早安」
  for (const g of GREETS) if (h >= g[0]) cur = g;
  return [cur[1].replace(/\{name\}/g, name), cur[2]];
}
```

**同时把头像和用户名挪到顶栏**（原来藏在左下角侧栏底部）：

- 头像 52px，圆角，有图用图、没图用首字渐变底
- 右边两行：大字问候「下午好，阿龙。」+ 小字时段副标题带对应小图标（☀️🌤️🍚⛅🌇🌙🌛）
- 点头像直接进「我的」（用户习惯把头像当入口）
- 问候语字号从 14px 提到 `clamp(17px, 1.6vw, 21px)`

**两个踩过的坑**：

- **昵称去重**：`nickname` 常是「张老师」，拼成「张老师，上午好」会叠字，所以去掉结尾的「老师」。但如果只在渲染时去、在时钟 tick 时不去，跨时段那一刻文字会变成「张，上午好」——两边必须用同一套取名规则。
- **`data-goto` 被覆盖**：首页 `bindHome` 里如果 `querySelectorAll('[data-goto]')` 全局绑，视图自己的 `bindTabs(main)` 会再覆盖一次。所以只选 `.ah-btn[data-goto]`。

**验证**：三端（390×844 / 820×1180 / 1440×900）都正常，问候语「下午好，阿龙。」+「⛅ 还有半天，够把一件难事推进一大步。」，点头像 hash 变 `#/me`。

### 6. 课时单价改不了 + 默认应该是 30 元

**「改不了」的根因**：`publicUser()` 的返回值里漏了 `settings`。前端 `state.user` 来自 `/auth/me` 和 `/me`，不含 `settings` 就意味着**单价永远读回默认值**——用户在「单价」里改成别的数字，保存后刷新又变回去。（`/api/me` 接口本身是单独读原始列返回的，但前端 `renderLessons` 用的那次请求没拿到。）

代码里其实已经有 `settings: j(u.settings, {})` 了，这次补了注释防回归。

**「默认 30」的改法**：4 处 60 改 30，并抽成常量：

```js
// public/js/work.js
const DEFAULT_PRICE = 30;
// server/index.mjs
function buildLessonSummary(rows, pricePerHour = 30)
const price = Number(st?.lesson?.pricePerHour) || 30;   // 两处
```

**顺带堵住口径不一致**：服务端 `/api/lessons/summary` 现在把最终采用的单价回传（`price_per_hour`），前端以它为准。否则「单价显示 30、金额按 60 算」这种账对不上的情况迟早出现。

**验证**：单价按钮显示「单价 30 元/节」→ 记一节课的金额默认值 `30` → 改成 35 → 按钮变「单价 35 元/节」→ 改回 30 正常。

### 7. 新增「备课」模块

用户原话：

> 工作中需要增加一个备课模块，这里需要记录我备课的内容，因为有时候我不记得我备课备到哪里了。看了这个之后以后就不会忘记了。

**设计取向**：痛点不是「没有教案」，是**记不清备到哪了**。所以每条记录必须能回答三件事：给哪个班备（`class_name`）、备的是哪一课（`topic`）、备到哪一步（`progress` + `next_step`）。

页面结构按「先答断点，再查历史」排：

1. **最上面单独一块「接着备这些」**——只放还没备完的，每条右边浅黄底显示「下一步：……」或「进度：……」，点一下直接进编辑。这是整个模块的核心，解决「不记得备到哪」。
2. **筛选条**：按班级（从数据里自动聚合）、按状态（在备/备好了）、关键词搜索。
3. **完整清单**：左侧日期块 + 课题 + 状态 chip + 编号 + 班级/学科/时长 + 断点框 + 备注，右侧「标记备好」一键切换。

**和「上课」分成两张表的原因**：课上完记一条；备课发生在课前，一节课可能备两次，也可能一次备两节。用 `lesson_id` 松松挂一下（选填），不做强关联。

**表结构**（`server/db.mjs`）：

```sql
CREATE TABLE IF NOT EXISTS preps(
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  seq INTEGER,
  date TEXT,                    -- 备课日期 YYYY-MM-DD
  class_name TEXT DEFAULT '',   -- 给哪个班备的
  subject TEXT DEFAULT '',      -- 学科
  topic TEXT NOT NULL,          -- 课题，如《劝学》第三段
  progress TEXT DEFAULT '',     -- 备到哪了
  next_step TEXT DEFAULT '',    -- 下次接着备什么
  minutes INTEGER DEFAULT 0,    -- 花了多少分钟（选填）
  status TEXT DEFAULT 'doing',  -- doing 在备 / done 备好了
  lesson_id INTEGER,            -- 关联到哪节上课记录（选填）
  remark TEXT DEFAULT '',
  created_at TEXT, updated_at TEXT, deleted_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_preps_user ON preps(user_id, date);
```

接入通用 CRUD：`CRUD.preps` 字段表、`SEQ_SCOPE.preps='prep'`、排序 `date DESC, id DESC`、回收站标题、备份表清单、恢复白名单。

**一个输入体验的细节**：搜索框边打边筛时**只重画列表容器**，不整页重绘。整页重绘会重建输入框，光标和中文输入法候选框都丢，表现为「打一个字跳一次」。

**备字段写法也统一了**：见下一条。

**验证**：接口 CRUD 全通（create/patch/list/delete），seq 正常递增，回收站能查到；三端布局无溢出；「接着备这些」正确区分在备/已备好。

### 8. 备注要像第一行那样重点显示，加方框

用户原话：

> 备注时要像第一行那样重点显示，不然用户不知道这个备注可以写文字，需要增加方框。

### 这轮最值得记住的三件事

**1. 同一个现象背后可能有两层根因，只修表层等于没修。**
角标不消失：表层是「没重新拉未读数」，深层是「节点压根不存在，改 textContent 是改空气」。
移除头像没反应：表层是 `confirmDialog` 竞态，深层是服务端通配路由把具体路由截胡了。

**2. 路由匹配按注册顺序取第一个，是个定时炸弹。**
`/api/:table/:id` 这种总入口只要注册得早，就会吃掉后面所有同形状的具体路由。这次不是逐个加白名单，而是改成「写死字符多的优先」，一次修好 `/api/me/avatar`、`/api/teachers/:id`、`/api/attachments/:id` 三处。

**3. 「不能用」有时候不是 bug，是没配。**
换绑收不到验证码，代码路径全通，是 `.env` 里短信密钥空着。这种情况前端要**把话说清楚**（「本站没配短信服务」），而不是让用户对着「获取验证码」按钮反复点。

## 第三十五节 免注册登录：代码做完了，卡在一把短信密钥上

### 一、用户到底要什么

> 「我可以直接使用 workbuddy 登录我的工作台，这样我就不用再去注册账号了，另外我绑定了微信或者 QQ 以及手机号等，只要我扫码登录 QQ 或者微信、手机号等，就可以进入这个平台。如果我的微信或者 QQ 等其他账号登录了，可以自动获取当前状态登录。」

拆开是三条并列的需求，风险差别很大，不能混着回答：

| 需求 | 技术可行性 | 前置条件 | 现在的状态 |
|---|---|---|---|
| 手机号 + 验证码**免注册**登录 | 完全可行 | 需要一个能真发短信的通道（要花钱、要实名） | 代码已上线，**等密钥** |
| 微信 / QQ 扫码，扫码后自动建号进入 | 技术可行 | 微信开放平台「网站应用」需**企业资质**；QQ 互联同样要求主体资质 | 未接入，个人号申请不下来 |
| 直接用 WorkBuddy 账号登录 | 技术可行 | 企业认证 + 已备案官网 + 有代码签名客户端 + 7 工作日审核 | 未接入，OAuth 代码已写好等凭证 |

结论先说：**只有第一条现在能真正通**，而且缺的最后一样东西不在代码里——是短信服务商的密钥。

### 二、免注册登录是怎么做的

原来的 `/api/auth/login` 有个前提：手机号必须在 `users` 表里存在，否则 404「该手机号还未注册」。用户的原话是「不想再去注册账号」，所以验证码模式下必须能**凭空长出账号**。

改动落在三个地方，缺一不可：

```js
if (!u && b.mode !== 'password') {
  if (!CONFIG.allowRegister) fail(404, '该手机号还未注册，请联系管理员开通', { needRegister: true });
  const opt0 = one('SELECT * FROM otps WHERE phone=?', phone);
  if (!opt0 || String(opt0.code) !== String(b.code || '')) fail(400, '验证码不正确');
  if (Date.now() > Number(opt0.expires_at)) fail(400, '验证码已过期，请重新获取');
  const r = run('INSERT INTO users(phone,password_hash,nickname,created_at,updated_at) VALUES(?,?,?,?,?)',
    phone, null, '老师' + phone.slice(-4), nowISO(), nowISO());
  const uid0 = Number(r.lastInsertRowid);
  seedUserData(uid0);                              // 不灌种子数据，进来是个空台子，用户以为坏了
  run('DELETE FROM otps WHERE phone=?', phone);    // 用过即焚
  ...
  return { user: publicUser(u), token: t0, created: true };
}
```

**建号必须过三道关，少一道就是个任意注册漏洞**：

1. **只能是 otp 模式**。密码模式绝不能凭空建号——否则只要知道密码格式，任何人都能批量造账号。
2. **验证码必须真的发出去过、没过期、一次一用**。`DELETE FROM otps` 那行是「用过即焚」：同一条码不能拿去登录两次，也不能拿去给第二个人建号。
3. **`ALLOW_REGISTER=1` 开关**。关掉就退回老行为。这个开关不是装饰，是留给「哪天想把门关死」的退路。

新账号昵称取手机尾四位（`老师7777`），因为注册这一步不该问用户「你叫什么」——多一个必填项就多一批放弃的人。名字进到「我的」里随时能改。

### 三、短信通道：三种接法，选一种

`server/sms.mjs` 是一个适配层，认出哪家就调哪家的签名算法，三家都不配就返回 `notConfigured`，由上层决定降级。

```js
export function smsChannel() {
  if (CONFIG.smsWebhookUrl) return 'webhook';
  if (CONFIG.smsAccessKeyId && CONFIG.smsAccessKeySecret) return 'aliyun';
  if (CONFIG.smsSecretId && CONFIG.smsSecretKey && CONFIG.smsSdkAppId) return 'tencent';
  return '';
}
```

| 方式 | 要填的变量 | 适合谁 | 备注 |
|---|---|---|---|
| **阿里云** | `SMS_ACCESS_KEY_ID`<br>`SMS_ACCESS_KEY_SECRET`<br>`SMS_SIGN_NAME`<br>`SMS_TEMPLATE_CODE` | 已有阿里云账号的人 | 签名要报备（1–2 工作日），模板要审核，内容须含 `${code}` |
| **腾讯云** | `SMS_SECRET_ID`<br>`SMS_SECRET_KEY`<br>`SMS_SDK_APP_ID`<br>`SMS_REGION`（默认 ap-guangzhou）<br>`SMS_SIGN_NAME`<br>`SMS_TEMPLATE_CODE` | 已有腾讯云账号的人 | 模板参数是 `${1}`（验证码）和 `${2}`（有效期），顺序不能反 |
| **通用 webhook** | `SMS_WEBHOOK_URL`<br>`SMS_WEBHOOK_TOKEN`（可选） | 自己搭转发、或用了别家服务 | 收 `POST {phone, code, template, text}`，返回 2xx 即视为成功 |

填完不用改代码，重启服务后 `/api/auth/config` 的 `smsEnabled` 会自己变 `true`，登录页的「验证码登录」标签就会从「未开通」变成正常可用。

### 四、没配短信时，界面必须自己说清楚

这一轮顺手补的，也是上一轮暴露出来的老问题：**代码路径全通、就是发不出短信，用户只会反复点按钮**。

以前的做法是「`smsEnabled` 为假就整个标签不渲染」。看着干净，实际很糟——用户知道有「收码就进」这个功能，进来发现入口不见了，第一反应是「没做」，而不是「差个密钥」。

现在两处都改了：

- **标签保留，挂角标**：`验证码登录` 后面跟一个小小的「未开通」，灰色，选中时变琥珀色。功能存在、状态明确。
- **面板顶部一条说明**：「验证码登录暂未开通 / 站点还没配短信通道，验证码发不出去。请先用下面的「密码登录」进入，一切功能都不受影响。」按钮同步 `disabled`，不让人白按一次。
- **密码面板加一句**：没短信时提示「如忘记密码，需在服务器上重置（见 README 第九节）」；有短信时才说「用验证码登录后自助重置」。这两句话不能混着说，否则用户会照着做不到的路径去试。

底层 `/api/auth/otp` 在 `!demoMode && !hasChannel` 时返回 `501 + { smsNotConfigured: true }`，前端认这个标记弹专门的提示，而不是笼统的「操作失败」。

### 六、微信 / QQ / WorkBuddy 这三条，为什么还开不了

不是没写，是**资质门槛在个人开发者之上**：

| 渠道 | 卡在哪 | 代码状态 |
|---|---|---|
| 微信扫码 | 开放平台「网站应用」要求企业主体 + 已备案域名；个人主体只能申请公众号，拿不到网站扫码登录 | `WX_APPID` / `WX_APPSECRET` 已预留，**OAuth 换用户的逻辑还没写** |
| QQ 扫码 | QQ 互联同样要求企业主体备案 | `QQ_APPID` / `QQ_APPKEY` 已预留，同上 |
| WorkBuddy | 企业认证 + 备案官网 + 有代码签名的 Windows/macOS 客户端 + 7 工作日审核 | **OAuth 全流程已实现**，只差 `WORKBUDDY_CLIENT_ID` / `WORKBUDDY_CLIENT_SECRET` / `WORKBUDDY_REDIRECT_URI` |

有一个必须先说清的**认知偏差**，否则用户会白等：

> 「我的微信已经登录了，网站应该能自动拿到我的微信身份」——**不能**。浏览器里的微信登录态和第三方网站之间没有任何共享通道，任何网站要拿微信身份，都必须走一次「跳转到微信授权页 → 用户点确认 → 回跳带 code」，这是 OAuth 的规定动作，没有「静默自动获取」这条路。

扫码入口现在是灰的，点了会明确说「尚未开通，请用密码登录」，不会再画一张假二维码糊弄。

### 七、这一节的教训

**1. 「功能没做」和「功能做了但没配」在用户眼里一模一样。**
唯一的区别是界面上有没有一句话。短信这种「代码全通、差一把钥匙」的情况，必须在入口处标明状态，而不是把入口藏起来。藏起来最省事，也最伤人。

**2. 免注册 = 任意注册，除非三道关都锁着。**
「验证码对了就建号」这条逻辑本身是开放注册的口子。所以模式、验证码、开关三道关一道都不能省，尤其是「用过即焚」——没有它，一条码能建无数个号。

**3. 用户说的「自动获取状态」，技术上往往不存在。**
微信/QQ 的登录态不能跨站共享，这是浏览器的同源策略和 OAuth 的授权模型共同决定的。与其写个看似智能实则一直失败的功能，不如把真实路径讲清楚：点一下、确认一下、进来。

**4. 默认值改一次，要顺带查一遍「谁在别处又写了一遍」。**
课时单价从 60 改 30 时，前端 `DEFAULT_PRICE`、服务端 `buildLessonSummary(rows, pricePerHour = 30)`、两处 `|| 30` 一共四处。少改一处就会出现「显示 30、按 60 算钱」。最后让服务端把 `price_per_hour` 回传给前端，才算把口径统一到一处。

## 第三十六节 忘记密码：一条不需要短信、也不需要用户碰终端的路

### 一、上一节留下的死角

上一节把「验证码登录未开通」写到了界面上，这是对的，但只解决了一半问题。
真正扎人的场景是：**没配短信 + 密码想不起来**。这时候：

- 验证码登录：走不通（发不出码）
- 密码登录：也不通（密码忘了）
- 界面上的提示原文是「需在服务器上重置（见 README 第九节）」

对一个不碰终端的人来说，这句话等于「你进不来了」。README 写得再清楚，他也不会去看。

### 二、做法：取件码 + 一条现成命令

```
用户填手机号 → 服务端生成 8 位取件码（30 分钟、一次性）
             → 页面同时给出取件码和整条命令
             → 有服务器权限的人执行那条命令
             → 用户点「我已重置，去登录」
```

命令长这样，页面上一键复制：

```bash
node "/绝对路径/tools/reset-by-code.mjs" 70378479 '新密码'
```

不带新密码执行时只做校验并报出对应账号（防止改错人）：

```
✅ 取件码有效，对应账号：13800138000（阿龙）
   还剩 30 分钟有效期。
```

### 三、为什么不做成「填码就改密码」

这是这一节唯一需要想清楚的设计判断：

> **取件码本身就印在这个页面上。** 任何能看到这行字的人都能改密码，那等于没有验证。

只有「必须有人去服务器上执行」才构成一道真门。而这道门用户本来就过得了——他找得到人。
换句话说，这个设计的门槛不是密码学，是**社会工程**：要改密码，得让一个对这台机器有权限的人动手。

配套的几道小闸：

| 措施 | 防的是什么 |
|---|---|
| 8 位随机数（`crypto.randomInt`） | 猜码 |
| 30 分钟过期 | 截图留存后长期有效 |
| `used_at` 用掉即焚 | 同一个码改两次 |
| 一号码只留一条（`phone` 主键） | 旧码还能用造成的混乱 |
| 同号 60 秒一次 / 每天 10 次 | 接口被刷 |
| 密码至少 6 位（与注册一致） | 规则不一致导致的「重置完还是登不上」 |
| 重置后 `UPDATE sessions SET revoked=1` | 旧设备继续持有登录态 |

### 四、一个刻意做「错」的地方：不回「该手机号未注册」

`POST /api/auth/forgot` 对**没注册过的手机号也返回一个码**。看起来像 bug，其实是故意的：

如果它回「该手机号未注册」，这个公开接口就变成了**手机号枚举器**——拿一批号码跑一遍，就能知道谁是你这个站点的用户。

所以：公网接口一律不透露账号是否存在。真相只在终端里说，而能看到终端的人本来就能直接查库：

```
❌ 手机号 13900000000 没有对应账号。请确认登录页填的号码是否正确。
```

### 五、`sheet is not defined` —— 一个只有真点一次才会暴露的错

`forgotSheet()` 里调了 `sheet({ title, body })`，但 `ui.js` 顶部只从 `core.js` 导入了
`api, el, esc, toast, ls`——**`sheet` 是后加的，忘了补进 import**。

`node --check` 检查不出来（语法合法），构建也不报（ESM 的未定义变量是运行时的 ReferenceError），
只有在浏览器里真点一下「忘记密码」才会看到控制台那一行。

教训很直白：**语法检查过 ≠ 能用**。凡是新增了跨模块调用的函数，必须真跑一遍那条交互路径。

### 六、验证记录

本地：

| 用例 | 结果 |
|---|---|
| 生成取件码 | `200`，8 位，`expires_in: 1800`，命令含绝对路径 |
| 60 秒内重复生成 | `429 刚生成过一次，请 57 秒后再试` |
| 手机号格式错 | `400 请输入正确的手机号` |
| 只校验不重置 | 打印账号 + 剩余分钟 + 提示补密码 |
| 码不存在 | `❌ 取件码 99999999 不存在` |
| 密码太短 | `❌ 密码至少 6 位` |
| 真正重置 | `✅ 已重置 … 同时注销了 2 个已登录设备` |
| 同一个码再用 | `❌ 这个取件码已经用过了` |
| 新密码登录 | `200`，用户 `阿龙` |
| 状态查询 `/api/auth/forgot/:phone` | `{used: true, expired: false, reset_at: ...}` |

浏览器（390×844 / 1440×900）：弹窗正常、手机号自动预填、取件码显示、复制按钮可用、点「我已重置」正常关闭、横向溢出 0px、JS 错误 0。

线上 `wb-v25`：完整走了一遍「密码登录 → 忘记密码 → 生成取件码 → 命令复位 → 用新密码登录 → `#/home` + 「下午好，阿龙。」」。

### 七、教训

**1. 兜底流程要交给用户能真的完成的那一环。**
「去看 README 第九节」是我写的，不是他能做的。把它换成「点这里，复制这行字，发给我」，才是条路。

**2. 公开接口宁可「一视同仁地成功」，也不要「诚实地报错」。**
「该手机号未注册」这种诚实，在公开接口上就是信息泄漏。诚实要放在有权限的地方说。

**3. 新增跨模块调用，必须真点一次。**
`sheet` 忘了 import，`node --check` 和构建都放行。这类错误的共同点是：静态检查看不见，浏览器一点就现原形。

## 第三十七节 登录注册全链路体检：46 项里挂了 5 项，4 个是真 bug

用户的原话是「测试人员再测试一遍登录注册这块逻辑，感觉现在很多都不能使用」。
「感觉」两个字很关键——他没说哪一条坏，所以我把它当成一个黑盒功能，从用户视角把每个能点的地方点一遍。

### 一、体检查了什么

两轮，共 46 项：

| 组 | 内容 | 项数 |
|---|---|---|
| A | 登录页初始状态（标题、标签、说明条、按钮禁用态） | 4 |
| B | 密码登录（错密码、对密码、按钮恢复、欢迎语带名字） | 5 |
| C | 刷新后保持登录 | 1 |
| D | 我的页 / 账号安全 / 改密码 / 绑定面板 / 退出 | 12 |
| E | 未勾协议被拦 | 2 |
| F | 注册页（未配短信时的表现） | 4 |
| G | 忘记密码 / 取件码 / 命令校验 | 6 |
| H | 第三方入口（微信、QQ、WorkBuddy） | 4 |
| I | 全流程 JS 错误 | 1 |
| J | 服务端接口边界（假绑定、解绑、会话设备名） | 6 |

第一轮 26 项挂了 5 项。逐条查下来，**4 个是真 bug，1 个是我自己把测试写错了**。

### 二、真 bug 1：微信 / QQ 绑定一直在写假 openid（最严重）

```js
if (type === 'wechat' || type === 'qq') {
  const openid = `${type}_demo_${u.id}`;   // ← 假的，跟微信没有任何关系
  ...
}
```

这个分支从来没读过 `oauth_states.purpose`（虽然库里会写 `bind-wechat`）。
结果是：**任何登录用户点一下「去绑定微信」，服务端就给他写上一个 `wechat_demo_1` 这种假值，界面显示「微信 已绑定」。**

两个后果，第二个更糟：

1. 用户以为绑好了。以后真去扫码时，系统会把这条假绑定当成真的。
2. `/api/auth/unbind` 允许「有微信绑定就解绑手机号」。假绑定 + 解绑手机号 = 一个只有假 openid、没有手机号的账号，**两条登录路都走不通，账号报废**。

体检时就是这么中招的：测试账号解绑手机号、再解绑微信（被拦）、然后被清理——`users` 表里留下一条 `id=7, phone=NULL, wx_openid='wechat_demo_7'` 的僵尸记录。

修法是双向的：

- **服务端**：没配 `WX_APPID` / `QQ_APPID` 就返回 501「尚未开通」；配了也必须走 OAuth 回调写 openid，**客户端传什么都不认**——认了等于任何人可以声称自己是任何人。
- **前端**：`me.js` 的绑定按钮先查 `AUTH_CFG.qrEnabled`，没开通就明说，**一个假二维码都不给**。

### 三、真 bug 2：登录后立刻切页会被弹回首页

```js
state.user = r.user; location.hash = '#/home';   // ① 改 hash，触发 hashchange → render()
await loadMe();                                   // ② 等网络
render();                                         // ③ 又渲染了一次
```

问题在 ② 到 ③ 之间：`render()` 读的是**当时的 `location.hash`**。
如果用户在这段空档里点了别的页面（比如登录后顺手点「我的」），③ 会拿新 hash 渲染一次，
但 `loadMe()` 还没回来时 `state.user` 可能刚好被重置，于是渲染回首页，把用户刚点的页面顶掉。

实测表现：登录后立刻跳 `#/me`，约 1/8 概率停在首页，且 URL 是 `#/me` 但内容是 home——**地址和内容对不上**。

修法：把顺序固定成「先取数据，再改 hash，最后渲染」：

```js
state.user = r.user; await loadMe(); location.hash = '#/home'; render();
```

四处登录入口（密码、验证码、扫码、注册）全部统一。改完连跑 4 次稳定。

### 四、真 bug 3：注册页在没配短信时是个「假入口」

没配短信时，注册页照样长出四个输入框和两颗亮着的按钮。用户会认认真真填完手机号、称呼、密码，
最后卡在「获取验证码」上——而那句话是「未配置短信通道」，等于让他去改自己改不了的东西。

改法：和验证码登录页一致——顶部一条说明 + 两颗按钮 `disabled`：

> **注册需要短信验证码，本站暂未配置短信通道**
> 没配短信就没法证明手机号是你的，所以这里暂时注册不了。如果是你自己在用，直接用手机号 + 密码登录即可。

另外补了前端前置校验（手机号格式、6 位验证码、密码长度），别让用户提交一个注定失败的表单再去猜哪里错了。

### 五、真 bug 4：改密码成功后「无声关闭」

原来点「保存新密码」→ 请求成功 → 面板立刻关掉 → 弹一个 2.4 秒的 toast。
问题是**失败时面板不关**。于是「关掉了」和「没关」成了唯一线索，用户松手之后还得回想刚才发生了什么。

改成留在原地，把结果写进面板：

```
✓ 密码已更新
其他设备上的登录还在。如果这个账号可能被别人用过，建议一并退出。
              [知道了]  [退出其他设备]
```

失败时（原密码错）把光标放回原密码那格并全选，省得用户自己找。

### 六、顺手修的两个小问题

**6.1 会话列表出现空白设备行**
不经过 `createSession()` 建的会话（历史数据、脚本注入）`device` 是空串，界面上就是一行空白，
用户根本认不出那是哪台设备，更不敢点「退出其他所有设备」。现在兜底成「未知设备」，并把「本设备」排到最前面。

**6.2 我自己写错的断言**
第一轮有两条挂的是测试脚本的问题，不是产品的问题：

- `全流程 JS 错误 0` —— 控制台里那条 `400 Bad Request` 是「故意用错密码登录」的正常结果。断言该排除网络层噪声，只看真正的 `pageerror`。
- `未勾协议 → 没进首页` —— 登录页本身就在 `#/home` 上（未登录时 hash 是 `/home` 也渲染登录页），拿 hash 字面值判断是错的。应该看「有没有 `.auth`、有没有 `#greet-line`」。

记这一条是因为：**测试写错和代码写错，现象一模一样。**不逐条查下去，就会把产品改坏去迎合一个错误的断言。

### 七、一个差点被当成 bug 的现象

体检中途出现「调用 `set-password.mjs` 之后，浏览器立刻退回登录页」。
第一反应是「会话管理坏了」，查下去发现：`set-password.mjs` 会执行 `UPDATE sessions SET revoked=1`——
**这是它故意的设计**，改密码就该踢掉所有设备。测试脚本却还想拿旧会话继续跑，所以一刷新就掉线。

这条留在 README 里当提醒：改密码类脚本「踢会话」是特性不是缺陷，
任何自动化测试在它之后都必须重新登录，不能指望旧标签页还活着。

### 八、最终结果

| 轮次 | 通过 | 说明 |
|---|---|---|
| 接口层首轮 | 21/26 | 5 项失败 → 定位出假绑定、会话名等 |
| 浏览器全链路 | 44/46 → **46/46** | 修完 4 个真 bug 后全绿 |

三端（390×844 / 820×1180 / 1440×900）登录页、取件码弹窗、注册页横向溢出全部 **0px**，JS 错误 0。

线上 `wb-v26` 复验 11 项全部通过：标签角标、忘记密码入口、密码登录、欢迎语「下午好，阿龙。」、
我的页 9 项菜单、绑定面板「未绑定」、设备名「本设备」、点微信绑定明确回「尚未开通」。

### 九、这一节的教训

**1. 「简化版」和「假实现」只差一行注释的距离。**
`wechat_demo_${u.id}` 当初大概是想「先占个位，以后接真正的 OAuth」。但它写进的是一张**会被当真**的表，
而另一处业务逻辑（解绑手机号）恰好依赖这张表。占位符一旦参与判断，就成了漏洞。

**2. 顺序即正确性。**
`改 hash → 等网络 → 渲染` 和 `等网络 → 改 hash → 渲染` 只差一个顺序，后者才对。
只要 `render()` 依赖 `location.hash`，任何「先改 hash 再 await」的写法都是在赌用户不会在这段时间里点东西。

**3. 「没反应」和「做完了」在界面上必须长得不一样。**
改密码成功后面板一闪就关，和失败时面板留着——两种体验唯一的区别是「关没关」，
这个信号太弱。成功要有成功的样子。

**4. 测试写错时，最难的不是发现，是不去改产品迎合它。**
两条错误断言如果当时「顺手改一下产品」让它变绿，就会真的把登录页的 hash 判断改坏。

## 第三十八节 测试通行证：让「没配短信」不再等于「注册功能不可用」

### 一、需求

> 「我要自己去创建账号测试，你帮我生成一个线上的地址出来。以后每次更新都更新到这个地址上。」

线上地址一直是同一个，不需要每次换：

```
https://ad90e9b5065d6c06e.app.workbuddy.host/?sharecode=MAB7CEXA53
```

问题在下一句「我自己去创建账号」——**注册完全建立在验证码之上，而本站没配短信**。
上一节我把注册页改成了「按钮禁用 + 说明未配置」，那是对的做法，但它把用户锁在了门外：
他能看到功能，能理解为什么不能用，但就是不能用。

所以需要一个**可以被关掉、可以换掉、并且一看就知道是测试用的**验证入口。

### 二、设计：三条硬约束

```bash
ALLOW_TEST_PASSCODE=1
TEST_PASSCODE=826370        # 随机生成，不是 123456
```

| 约束 | 理由 |
|---|---|
| **默认关闭**，必须显式 `ALLOW_TEST_PASSCODE=1` | 不开就等于这块代码不存在，不会有「忘了关」的隐患 |
| **码从环境变量来**，每次可以重新生成 | 写死 `123456` 等于把后门焊死在门上，谁都知道密码 |
| **只在没有任何真实短信通道时生效** | 一旦 `.env` 填了短信密钥，这条捷径自动失效——能真发短信就不该再接受固定码 |

外加一条实现上的关键点：**它走的是完整的真实链路**，不是伪造一条用户记录。

```
点「获取验证码」 → 服务端把 826370 写进 otps 表
                → 前端自动填入输入框
                → 点「注册并登录」
                → /api/auth/register 照常校验 otps 表
                → 建号 → seedUserData() → 下发会话 Cookie
```

也就是说，它验证的是「注册逻辑本身对不对」，而不是绕过注册。这两件事的区别，在真出问题的时候会差出十万八千里。

### 三、界面上怎么区分

不能让人分不清「这是真短信」和「这是测试码」。三种状态三种长相：

| 状态 | 说明条 | 按钮 |
|---|---|---|
| 有短信通道 | 不显示 | 可用 |
| 没通道 + 有测试码 | **蓝色**「📱 短信通道未配置，已开启测试通道」 | 可用 |
| 没通道 + 没测试码 | **琥珀色**「验证码登录暂未开通」 | 禁用 |

刻意让「能用」和「不能用」用两种颜色：同一个黄色既表示「坏了」又表示「能凑合用」，会误导。

### 四、踩到的坑：先有鸡还是先有蛋

第一版逻辑写成了：

```js
const useTestPass = testPassOn && String(b.code || '') === CONFIG.testPasscode;
```

看着合理——「有测试通行证，并且用户填的码等于测试码」。但它意味着：
**用户必须先知道测试码，才能拿到测试码。** 因为「获取验证码」这一步本身就被这个判断拦住了，
直接返回 501「未配置短信通道」。第一次 curl 就是这个结果。

正确的位置是：`/api/auth/otp` 只要有测试通行证就发码，
**真正的校验放在 `/api/auth/register` 和 `/api/auth/login`**——那里比对 `otps` 表里存的值。
边界在哪，校验就该在哪。

### 七、教训

**1. 「不让他做」和「让他能做」都要说清楚。**
上一节把注册按钮禁掉是对的（假入口更糟），但只做到这一步不够。
用户的实际需求是「我要试一下」，那就得给一条他自己能走完的路，而不是一句「请联系管理员」。

**2. 校验的位置决定了功能能不能用。**
同一个判断放在「发码」处会把整条路锁死，放在「用码」处才是正确的边界。
写安全逻辑时先问一句：**这一步是「发」还是「用」？**

**3. 测试通道必须长得像测试通道。**
蓝色说明条、显式的环境变量、可随时关闭——三件事加起来，才让它不至于哪天变成真正的后门。

## 第三十九节 扫码登录：从「画个图案」到真能扫

### 一、需求

> 「请把登录那块全部打通」

上一轮体检完，登录矩阵是这样的：

| 入口 | 状态 |
|---|---|
| 验证码登录 / 注册 | ✅ 通（测试码 826370） |
| 密码登录 | ✅ 通 |
| **扫码登录** | ❌ **假的** |
| 微信 / QQ 登录 | ⛔ 需企业资质，代码侧补不了 |
| WorkBuddy 登录 | ⛔ 同上 |

「假的」具体是三件事凑在一起：

1. `drawQR()` 用 `Math.random()` 画了一张**看着像**二维码的图案，手机扫上去没有任何反应；
2. `loginQR()` 里有一颗「点此模拟手机已确认」的按钮，点下去直接调 `/auth/qr/:id/confirm`；
3. 而那个接口要 `requireUser` —— 未登录的人点它，等于**自己给自己发授权**。

也就是说，界面上那颗按钮，最好听的说法是「装饰」，最实在的说法是「假装能用」。

### 二、能打通的和打不通的，先说清楚

| 入口 | 结论 |
|---|---|
| **本站扫码登录** | ✅ 现在打通了。自己生成二维码 + 手机确认页，手机↔电脑↔iPad 一码登录 |
| 微信扫码登录 | ⛔ 需企业认证 + 已备案官网 + 审核，我没有代办权限 |
| QQ 扫码登录 | ⛔ 同上 |
| WorkBuddy 统一登录 | ⛔ 同上（`.env` 里三个空位已备好） |

所以这一节只讲第一行，但它是**真能用的那一行**。

### 三、自己写一个二维码编码器

项目是零依赖部署（node 内置模块 + 前端原生 JS），不能 `npm i qrcode`。
于是有了 `server/qr.mjs` —— 422 行，按 ISO/IEC 18004 从零实现：

```
字节模式编码 → 分块 + Reed-Solomon 纠错 → 交织
  → 矩阵布置（定位/定时/校正/版本/格式信息） → 8 种掩码选优 → 输出 SVG
```

**为什么值得自己写而不是塞一张图片**：票据 id 每次都不同，图必须现场生成；
而且零依赖是这套部署的前提，加一个包就破坏了「拷过去就能跑」。

#### 调试过程：从 0/10 到 10/10

用 OpenCV 的真实解码器验收，中间踩了六个坑。这些坑值得记下来，因为症状很不直观：

| # | Bug | 症状 | 根因 |
|---|---|---|---|
| 1 | `ecPerBlock` 除以两次块数 | 容量大一点就抛错 | 已经从 `CAP` 解构出 `blockCount`，又除了一遍 |
| 2 | 定位图形中心被挖空 | 完全扫不出来 | `d<=1` 写成白色，中心 3×3 成了白洞 |
| 3 | 掩码函数参数是 `(x,y)` | **前十几个字符对，后面乱码** | 公式里 i=行、j=列，传反了 |
| 4 | 格式信息位序错 | 部分版本能扫、部分不能 | 竖排/横排放位的分段索引算错 |
| 5 | 版本信息块写成 3×6 | **v7 以上整张无效** | 应是 6 行 × 3 列，写成了行列互换 |
| 6 | 跳过第 6 列时多减一次 | 右下角总有空格填不上 | `for` 自减之外又 `-= 1` |

第 6 个是我加的「空洞检查」自己抓出来的：

```js
for (let y = 0; y < size; y++)
  for (let x = 0; x < size; x++)
    if (!m[y][x]) throw new Error(`二维码布置有空洞：(${x},${y}) 未填，列对计算有误`);
```

> 静默留空会让码看着正常却扫不出来。宁可让它在生成时就炸，也不要让它悄悄发到用户手机上。

**最终验收**（真实 URL 内容，覆盖 v1→v8）：

#### 一个反直觉的发现：参考库本身有 bug

我一度拿 `python-qrcode` 的矩阵当标准答案逐格比对，结果怎么都不一致。
查到最后发现是**它错了**：

```python
# python-qrcode，map_data
for col in range(self.modules_count - 1, 0, -2):
    if col <= 6:
        col -= 1        # ← 改的是循环变量，range 的 -2 又叠上去
```

列对因此变成 `…8/7, 5/4, 2/1`，**第 3 列和第 0 列永远填不上**。
按 ISO 18004，正确序列是 `…8/7, 5/4, 3/2, 1/0`。

> 教训：不要用「看起来更权威的库」当唯一标准。当时如果我信了它，就会把自己正确的代码改坏。
> 最后的判据是真实解码器能不能扫出来，而不是谁跟谁一致。

### 四、安全模型：票据 ≠ 会话

这是整个设计里最要紧的一条。**扫码登录不是「扫了就进」。**

```
电脑                         服务器                      手机（已登录）
 │  POST /auth/qr            │                              │
 │ ────────────────────────▶ │ 建票据 pending，3 分钟有效    │
 │ ◀──── id + svg(二维码) ─── │                              │
 │                           │          扫码打开 /#/qr?id=…  │
 │                           │ ◀──────────────────────────── │
 │  GET /auth/qr/:id (2s轮询)│  peek：这是哪台设备、几点、谁  │
 │ ────────────────────────▶ │ ────────────────────────────▶ │
 │      pending              │                              │ 人工判断
 │                           │ ◀──── POST /:id/confirm ───── │ ← 唯一的安全边界
 │                           │      requireUser（Cookie）     │
 │      confirmed + token    │ 票据删除（一次性）             │
 │ ◀──────────────────────── │                              │
 │  POST /auth/qr/exchange   │                              │
 │ ◀──── Set-Cookie ──────── │                              │
```

三条硬规矩：

**1. 确认动作必须 `requireUser`。**
身份只认会话 Cookie，客户端传什么都不认。一张被转发出去的二维码，
拿到它的人如果没登录，只会被引导先登录自己——然后看到「有设备请求登录」，
那一台是别人的电脑。他确认的也是**他自己**的账号登上别人的电脑，害的是自己。

**2. 票据 ≠ 会话，必须换。**
轮询拿到的是 `token`，要再 `POST /auth/qr/exchange` 才拿到 Cookie。
为什么不在轮询响应里直接 `Set-Cookie`：轮询是前端定时 `fetch`，
中间可能被缓存/预取，`Set-Cookie` 的时机不可靠，失败也没法重试。

**3. 票据一次性。**
`confirmed` 之后立刻 `DELETE`。别人拿着同一个 id 再问，只会拿到 `expired`。

### 五、几个容易踩的工程点

**二维码里必须放绝对地址。**
原来返回 `http://localhost:3000/#/qr?id=…` —— 真实手机扫了打不开。
反向代理后面按 `Host` 头推出来的常是内网地址，所以显式配：

```bash
SITE_URL=https://ad90e9b5065d6c06e.app.workbuddy.host
```

**`createSession(res, ...)` 的 `res` 可以为 null。**
扫码那条路没有 `res` 可写 Cookie（会话是发给「轮询的那台设备」的），
所以这个函数不能假设 `res` 存在。

**`qr_tickets` 要补列。**
`CREATE TABLE IF NOT EXISTS` 不会给已有表加字段，得用 `ensureColumns()`：

```js
ensureColumns('qr_tickets', {
  device: "TEXT DEFAULT ''",
  ip: "TEXT DEFAULT ''",
});
```

**确认页要在「是否登录」判断之前拦下来。**
它既要给已登录的人看（确认/拒绝），也要给未登录的人看（先登录再回来）。
走常规 `render()` 的话，未登录会直接被踢回登录页，扫码场景就断了。

**异步回调回来时，锚点可能已经不在页面上了。**
`peek` 和 `confirm` 都是网络往返，回来时 `#qrc-card` 可能已被替换或移除。
原来直接写 `document.getElementById('qrc-home2').onclick = ...`，
节点不在就抛 `TypeError`，用户侧表现是「点了没反应」。

```js
if (!card.isConnected) return;   // 每次 await 回来都重新确认一次
...
const home2 = document.getElementById('qrc-home2');
if (home2) home2.onclick = () => { location.hash = '#/home'; };
```

### 六、`qrEnabled` 这个字段骗了人

`/auth/config` 里原来只有一个 `qrEnabled`，含义是「微信/QQ 开放平台接没接」。
但界面上它看起来像「扫码登录能不能用」——于是 `false` 的时候，
一个**点了就能登录**的扫码 tab 被当成坏的。

现在拆成两个名字，各自只说一件事：

```js
qrEnabled: !!(CONFIG.wxAppId || CONFIG.qqAppId),   // 第三方扫码通道
siteQrLogin: true,                                  // 本站扫码登录，故意不可关闭
```

`siteQrLogin` 写成常量 `true` 是有意的：它不依赖任何第三方，
只要 `SITE_URL` 配好就永久可用，做成「不可关闭」才不会哪天被误判成故障。

### 八、同时修掉的两处误导

**1. 验证码 tab 的角标。**

一个诚实的提示，好过一个假二维码。

### 九、教训

**1. 「看起来能用」比「明显坏了」更贵。**
假二维码不会报错、不会崩，它只是安静地浪费每个人的时间——
用户扫了十次，每次都以为是自己的手机不行。

**2. 画得对不等于扫得出。**
六个 bug 里有五个在肉眼看来完全正常。判据只能是真实解码器，
观感不能参与判断。

**3. 测试脚本本身也会错，而且错得很像产品 bug。**
这一轮的 26 项里，先有 8 项红。逐条查下来，**6 项是脚本自己的问题**：
用了不存在的手机号、拿另一张票据去确认、选择器语法错、等得太短、路径写成 `send-code`。
只有 2 项是真 bug（`peek`/`confirm` 回来时节点已移除）。
**看到红先怀疑测试，看到绿也先怀疑测试。**

**4. 字段名一旦有歧义，就会有人按歧义去用。**
`qrEnabled` 只是个布尔值，但它让一个能用的功能被当成坏的，
还让我自己在上一轮的总结里写过一次错误判断。名字就该只指向一件事。
